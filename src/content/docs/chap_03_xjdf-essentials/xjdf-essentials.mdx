The Exchange Job Definition Format (XJDF) is designed to be a pure data interchange format. XJDF Documents are generated during application runtime in order to communicate with applications and devices. Each XJDF Document contains dedicated information optimized exclusively for the recipient. 

Technically, XJDF specifies two views on print which are related but not identical - the product view and the process view. The product view is the process independent product description and “describes the final product from the perspective of the print buyer. The customer or product designer will typically describe the desired final product without any knowledge of the manufacturing process” [@xjdf_ip1, chap. 2.2.1 "Product Intent and Processes"]. The product description includes, for instance, the size of the desired product, its paper quality, and the folding details if required. The product description is unconcerned with production details such as the production size of the sheet on which the product is later printed, or how the product is positioned on that sheet. All process-specific details are defined in the process view of the XJDF Document. The process view might describe in a very accurate way how each step in the production workflow process has to be accomplished, on which device, and at what time. The following figure illustrates both perspectives specified in an XJDF Document:

</figure>

The product view is based on Product elements containing a set of multiple Intent elements, such as FoldingIntent, LayoutIntent, BindingIntent, etc. Each Intent element is a container for a specific type of information. FoldingIntent contains, for example, all folding details of the desired product. The XJDF Specification provides a set of individual intent types in order to specify a wide range of print products. In addition to the product description, XJDF also defines the process steps executed in a printing house in order to manufacture the final product. **In XJDF, process steps are called processes.** A production workflow is a concatenation of processes. Each process defined in the XJDF Specification is “assumed to be executed by a single-purpose device” [@xjdf_ip1, chap. 5.1 "Combining Individual Process Steps"]. Examples of processes are ConventionalPrinting, DigitalPrinting, Cutting, Folding, etc. The XJDF Specification comes with a broad amount of individual processes. Each individual process is defined by its unique name, a description, and a set of input and output resources. A complete list of all processes are specified in chapter 5 “Processes” of the XJDF Specification. 

The two different views of XJDF enable users to write either a pure product description without any production knowledge, or to define detailed instructions for a production device. A combination of both is also valid. This makes the data format very adaptable to many situations in various environments. 


## Gray Boxes
Gray Box is a commonly used term in XJDF. The term has been taken over from JDF 1.x and describes something between a Black Box and a White Box. By definition, a Black Box is a device or a system where only the input and output parameters (interfaces) are known. In contrast, a White Box describes a device or a system in which the internals are also known. The term Gray Box describes something in between.
As XJDF enabled devices and applications may not only allow for the definition of input and output but for some additional internal configurations as well, devices and applications are conceptually Gray Boxes. **Although most of the XJDF integration is Black Box integration, XJDF does not differentiate. From the perspective of XJDF, each system being integrated is a Gray Box, and the corresponding XJDF document describes it.**

Even the simplest product description document for job submission describes a Gray Box. XJDF Documents containing a pure product description are primarily used in Web-To-Print environments, for example, to link a printing house with a Webshop, a public print broker platform, or even a customer’s ERP system with an MIS system for the purpose of automating the customer’s supply chain of print products. The following is an XJDF stub of a product description Gray Box:

```xml title="Example: Gray Box 'product description'"
<XJDF JobID="JOB-42" Types="Product"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

The `@Types` attribute is the attribute for defining Gray Boxes. When reading an XJDF Document, this attribute is one of the first attributes to be analyzed. Product description Gray Boxes can be recognized by `@Types` = "Product". The attribute value "`Product` specifies that the products that are described shall be produced without complete knowledge of the production workflow" [@xjdf_ip1, chap. 3 Table 3.1]. On job submission in a Web-To-Print environment, the definition of the product workflow is the primary task of the MIS system. The MIS system is the leading system for the entire production. Therefore, it is responsible for computing or selecting a production workflow in order to produce the desired product.

The production workflow defined by the MIS is nothing more than a concatenation of single processes. Each production device or application can cover both single and multiple processes. For instance, a folding machine covers the single process Folding, whereas a modern collecting machine may combine the processes of Collecting, Stitching and Trimming in order to finalize a magazine in one shot. Conceptually, the folding machine, as well as the collecting machine, are both Gray Boxes: 

<figure>
  <Image src={grayBoxes} alt="Gray Boxes 'Folding' and 'Collecting Stitching Trimming'" />
  <figcaption>Figure: Gray Boxes 'Folding' and 'Collecting Stitching Trimming'</figcaption>
</figure>

Once a production workflow is defined, the MIS system has to route the job from one Gray Box to the next. Each Gray Box has to be addressed by an individual XJDF Document. 

All processes needing to be executed by the receiving Gray Box have to be declared in the `@Types` attribute. The attribute `@Types` can either define the value “Product” as shown in the example before, or one or multiple process names. Here, an XJDF stub is used to address a Gray Box “Folding” (Folding Machine):

```xml title="Example: Gray Box 'Folding'"
<XJDF JobID="JOB-42" Types="Folding" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

In order to define an XJDF document addressing a Gray Box containing a single folding process, the `@Types` attribute value has to be set to the process’ name “Folding”. However, an XJDF Document can not only address a single process. The `@Types` attribute allows also a whitespace separated list of process names. When addressing a collecting machine which provides the processes Collecting, Stitching and Trimming, the XJDF stub is as follows:

```xml title="Example: Gray Box 'Collecting Stitching Trimming'"
<XJDF JobID="JOB-42" Types="Collecting Stitching Trimming" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

The attribute `@Types` can not only define one single attribute value. A whitespace separated list of process names is also valid. The upper stub defines the processes Collecting, Stitching and Trimming. The order of the items is relevant to the order in which the processes have to be executed. This example stipulates that Collecting has to be the first process in the row. After Collecting, the semi-product has to be stitched and, finally, trimmed.

A combination of process names along with the value “Product” is also valid. The following is a stub demonstrating this:

```xml title="Example: Combination of Gray Box and product description"
<XJDF JobID="JOB-42" Types="ConventionalPrinting Cutting Product"      
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

The combination of process names accompanying the value “Product” means that the production process is partially defined. In some cases, a partial definition of workflows is needed in specific XJDF production lines.


## Common XML Structure
Let’s start with an abstract XJDF Document which outlines the common XML structure. Elements which are only rarely used in real-world scenarios have been ignored in this context. 

Most examples in this chapter are excerpts of real-world documents and contain many details. However, the focus of this chapter lies in the structure of the XJDF documents. This means that, in this chapter, it is important to get an understanding of the structure of the XML elements in an XJDF document, rather than the exact details and their meaning. Most examples are picked up later again in order to dive deeper into the details. Here: An abstract XJDF element tree as a representation of the common XML structure in XJDF Documents:

```xml title="Example: Common XJDF Structure"
<XJDF JobID="5" Types="ProcessName_1 ProcessName_2" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <AuditPool />
    <Comment />
    <GeneralID />
    <ProductList>
        <Product>
            <Intent Name="SpecificIntent">
                <SpecificIntent />
            </Intent>
            <!-- further product intents go here -->

        </Product>
        <!-- further products go here -->

    </ProductList>
    <ResourceSet Name="SpecificResource">
        <Resource>
            <AmountPool />
            <Part />
            <SpecificResource />
        </Resource>
        <!-- further resources of the same type may go here -->

    </ResourceSet>
    <!-- further ResourceSets go here -->

</XJDF>
```

The four main elements in an XJDF Document are Product, Intent, ResourceSet, and Resource. All product and process information are structured and organized mainly by these four elements. There are clearly defined locations where each of these elements has to be written. Basically, each XJDF Document is organized as a list of Product, Intent, ResourceSet and Resource elements.

The order of all elements is given by the specification. “In general the order of elements is lexically sorted in ascending order. Exceptions to alphabetical sorting will be explicitly called out in the relevant sections. [...] Attributes NEED NOT be sorted within an element" [@xjdf_ip1, chap. 1.3.5.1 "Order of Child Elements"]. 

### XJDF Element
Each XJDF Document starts with the XJDF root node. The XJDF node can only occur once per document. The following is an example of an XJDF root node:

```xml title="Example: XJDF Element"
<XJDF JobID="JOB-42" Types="Folding" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

As an XJDF Document is always in the context of a particular job and is aimed at a specific Gray Box or product description, the attributes `@Types` and `@JobID` are mandatory. The attribute `@JobID` contains the unique identifier of the current job, whereas the attribute `@Types` contains the names of a logical processes covered by the Gray Box which the document is directed towards. “Product” is also a valid value for `@Types` when defining a product description.

The attribute `@xmlns` is a standard XML attribute and defines the namespace of an XML document. “XML namespaces provide a simple method for qualifying element and attribute names used in Extensible Markup Language documents by associating them with namespaces identified by URI references” [@xml_namespaces_2009]. The qualified namespace url for XJDF Documents in version 2.0 is `http://www.CIP4.org/JDFSchema_2_0`. The url will be unique for future XJDF versions. 

The XJDF root node can contain up to five different types of subnodes. All subnodes are optional. The subnodes AuditPool and ProductList can only appear once per document. The elements GeneralID, Comment, and ResourceSet may occur multiple times. 

### AuditPool Element
The element AuditPool can only occur once and is a container element, primarily for the post facto recorded results of a Gray Box. Most items listed in the AuditPool have already been published to the managing system as XJMF message as well in real-time when the event has occurred. XJMF is a messaging system that comes with XJDF and is explained in detail later in the chapter dealing with XJMF. 

Results in the AuditPool element are, for instance, logs of notifications that have occurred during processing of the job, resource consumption, or status information with the appropriate start and end times. The AuditPool is the relevant element for production data acquisition. "In contrast to most other elements in XJDF the child elements of AuditPool SHALL be ordered chronologically from oldest to newest rather than alphabetically" [@xjdf_ip1, chap. 3.4.1 "AuditPool"]. AuditPool Elements are typically part of XJDF Documents which are sent back to the management application after job completion. The following is an example of an AuditPool element:

```xml title="Example: AuditPool Element"
[...]
<AuditPool>
    <AuditCreated>
        <Header ID="I42" DeviceID="DEV_ID" Time="2016-12-28T10:45:05Z" />
    </AuditCreated>
    <AuditStatus>
        <Header ID="I43" DeviceID="DEV_ID" Time="2016-12-28T10:47:19Z" />
        <DeviceInfo Status="Production" Speed="6000">
            <JobPhase JobID="Job-42" JobPartID="Front" Status="InProgress"
                StartTime="2016-12-28T10:40:00Z" PercentCompleted="31.66"
                QueueEntryID="I434" Amount="1343" Waste="85"/>
        </DeviceInfo>
    </AuditStatus>
    <AuditNotification>
        <Header ID="I44" DeviceID="DEV_ID" Time="2016-12-28T10:49:26Z" />
        <Notification Class="Information">
            <Event EventID="3092" EventValue="Paper stock is low." />
        </Notification>
    </AuditNotification>
    [...]
</AuditPool>
[...]
```

Each status change, notification, etc. is listed chronologically in the AuditPool element. The AuditPool element allows multiple types of specific sub elements in order to protocol the production process of a Gray Box. The structure of the sub elements is streamlined to the structure of XJMF messages. In many situations, the AuditPool is just an aggregation of all XJMF messages produced and published by the system.

Examples of valid sub elements in the AuditPool element are, for instance, AuditNotification or AuditStatus. The AuditNotification element “logs individual events that occurred during processing” [@xjdf_ip1, chap. 3 Table 3.6 "AuditPool/AuditNotification"], whereas the AuditStatus “logs start and end times of any process states and sub-states” [@xjdf_ip1, chap. 3 Table 3.6 "AuditPool/AuditStatus"]. The full list of all sub elements can be read in the XJDF Specification.

Each specific Audit element contains at least a Header element. The Header element provides meta information about the specific audit entry such as the exact creation time or the identifier of the producing device. The log information itself is specified in an additional sub element of the specific audit element. For instance, the AuditStatus element requires another element DeviceInfo in order to specify the status information to be logged. 

### Comment Element
The element Comment is a common XJDF element. This means that there are multiple locations where this element can be written. One major location is as a child element of the XJDF element. The Comment element may exist multiple times at each location. 

Using comments always requires human interactions. Writing a comment assumes somebody will be reading and interpreting the comment during production. From the automation point of view, comments lead to less automated systems. The following is an example of a Comment element:

```xml title="Example: Comment Element"
<XJDF ...>
    [...]
    <Comment Type="Instruction" TimeStamp="2016-08-20T14:44:02+02:00" 
            PersonalID="cnorris">
        Please take a special care for the image on the upper right.
        This is the leading motive of the product.
    </Comment>
    <Comment Type="JobDescription" TimeStamp="2016-08-20T14:44:02+02:00" 
           PersonalID="cnorris">
       Flyer A6 
       4c both sides
       135 gsm glossy paper
    </Comment>
    <!-- further comments may go here -->
    [...]
</XJDF>
```

The metadata of the comment, such as the author or the timestamp, has to be written as attributes of the appropriate Comment element. The comment itself is an unformatted plain text and is the XML text value of the Comment element.
Comments are for human information only. A comment shall not influence the behavior of an application or device in any way. A device or application should not parse the comment for keywords in order to provide presettings or change its behavior based on this information. Doing so would cause compatibility issues between systems and increase the maintenance effort over time. 


### GeneralID Element
The third child node in the XJDF structure above is GeneralID. Just as the Comment element is a common one, so too is the GeneralID element. Apart from the depicted location in the common XML structure, there are additional locations where a GeneralID element can be written. A GeneralID element may also appear multiple times per location.

“GeneralID describes a generic identifier. The name or usage of the identifier is specified in `@IDUsage`, and the specific value of the variable is specified in `@IDValue`. The data type is specified in `@DataType`” [@xjdf_ip1, chap. 8.15 "GeneralID"].

```xml title="Example: GeneralID Element"
[...]
<GeneralID IDUsage="Height" DataType="integer" IDValue="1440"/>
<GeneralID IDUsage="Width" DataType="integer" IDValue="720"/>
[...]
```

The GeneralID example above shows two elements. The first element defines a height value and the second one a width value. This is just one usage of GeneralID. GeneralID is a very generic element and can be used as a key-value pair for almost any purpose. This is exactly what makes GeneralIDs susceptible to compatibility issues. When developing a new XJDF interface, developers tend to gladly use the GeneralID because they are able to externally map internal requirements on a one by one basis. This makes it very easy to design an XJDF interface but decreases the compatibility with standard applications enormously. Before using GeneralIDs, a better approach is to extend XJDF by a private namespace. Introducing and working with private namespaces is explained later in the chapter “Extensibility”.


### ProductList Element
The ProductList element can only exist once per document and contains the process independent product descriptions. It is recommended to provide a full product description of all products being processed within a Gray Box. This places each production step in the proper context. For example, when folding, it actually seems to be sufficient to provide only a JobID and some folding parameters. However, giving the full product description to the operator enables him/her to understand the final product, especially when working on just a single product part of a complex product. People need to know what they are working on. The product description provides the operator with the job context. This allows him to make ready more quickly and recognize irregularities in production more easily. Although the amount of automation in printing is increasing, manual workers are still dominating the production lines in printing houses. Most of the applications and devices are being controlled by humans. The XJDF Specification does not require a ProductList for each XJDF Document. At any rate, it is recommended to provide one and publish it to the operator. The following is an XJDF snippet of a ProductList element containing two individual print jobs:

```xml title="Example: ProductList Element"
[...]
<ProductList>
    <Product Amount="250" IsRoot="true">
        <Intent Name="ColorIntent">
            <ColorIntent>
                <SurfaceColor ColorsUsed="Cyan Magenta Yellow Black" 
                    Surface="Front"/>
            </ColorIntent>
        </Intent>
        <Intent Name="LayoutIntent">
            <LayoutIntent FinishedDimensions="1683.779 2383.937 0.0" 
                Sides="OneSided"/>
        </Intent>
        <Intent Name="MediaIntent">
            <MediaIntent MediaQuality="135_GLOSS"/>
        </Intent>
    </Product>
    <Product Amount="1000" IsRoot="true">
        <Intent Name="ColorIntent">
            <ColorIntent>
                <SurfaceColor ColorsUsed="Cyan Magenta Yellow Black" 
                    Surface="Front"/>
            </ColorIntent>
        </Intent>
        <Intent Name="LayoutIntent">
            <LayoutIntent FinishedDimensions="841.889 1190.551 0.0" 
                Sides="OneSided"/>
        </Intent>
        <Intent Name="MediaIntent">
            <MediaIntent MediaQuality="135_GLOSS"/>
        </Intent>
    </Product>
</ProductList>
[...]
```

The ProductList element contains two individual print products. The first product describes 250 posters in DIN A1 (594 mm x 841 mm), printed in four colors, one sided, on a 135 gsm glossy paper. The second product describes 1,000 posters in DIN A3 (297 mm x 420 mm), printed in four colors, one sided, on a 135 gsm glossy paper as well. Technically, each Product element contains an `@Amount` attribute as well as a list of Intent elements which defines the characteristics of the respective product. The ColorIntent describes all color issues, the LayoutIntent defines the details of the layout, while the MediaIntent is the container for customer requirements regarding the printing substrate. Beyond that, the XJDF Specification provides further intent types for the specification of a broad range of individual product characterizations. The full list of all intents can be found in the XJDF Specification in chapter 4 “Product Intent”. 

As soon as a ProductList contains more than a single Product element, the attribute `//Product/@IsRoot` has to be defined. If `@IsRoot` = “true”, “this Product element is a self-contained product. If false, this Product element is a child product of another one, such as a cover or insert” [@xjdf_ip1, chap. 4 Table 4.1 "Product/IsRoot"]. Using child products, more complex products can be expressed, such as a magazine with a special cover. Product descriptions are discussed in broad detail later. 


### ResourceSet Element
Both product descriptions, as well as process descriptions, require additional resources. In order to describe resources, XJDF specifies the Resource elements. Resource elements are child elements of ResourceSet elements and describe the physical or logical entities in a print production workflow. Resources of the same logical group such as the four printing plates of a print run or the artwork files provided by the customer for a single print job are sub elements of the same ResourceSet element. All ResourceSet elements are usually associated with a specific process but can also be associated with products. 

The following is an example of a RunList input resource. RunList resources reference the input and output files of processes, or can also be used in a product description in order to reference the files of the customer's original artwork, etc. 

```xml title="Example: RunList Resource"
[...]
<ResourceSet Name="RunList" Usage="Input" >
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/artwork/my.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
[...]
```

Most XJDF Documents contain several ResourceSet elements. A ResourceSet element is a container for a single resource or for a logical group of resources. ResourceSets are mainly used to describe input or output resources of processes. Each process normally has one or several input ResourceSets, but only a single output ResourceSet. ResourceSets can also be associated with a product description.


### XJDF Example: Folding
To conclude this section, a real-world XJDF folding example is presented. Folding is a very common finishing process in printing. The input resources of a folding machine are the flat paper plus some parameters of how to fold the flat paper (FoldingParams). The output resource is the folded product or product part. 

Since a folding machine is a single-purpose device it can be covered by a Gray Box containing only a single process “Folding”. Videos and images of what a folding machine looks like or how it works can be found online. Common search terms of folding machines are “Buckle Folding Machine”, or “Knife Folding Machine.”

This XJDF example anticipates many details of XJDF which are explained in detail later. Nevertheless, it makes sense to get an early preview of a real-world XJDF Document in order to place all items learned in the proper context. The snippet need not be understood completely at this point. Extracts of this example are presented again later in the book in order to explain the details and mechanisms behind XJDF.

```xml title="Example: XJDF Gray Box Folding"
<XJDF JobID="JOB-42" Types="Folding" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <AuditPool>
        <AuditCreated>
            <Header AgentName="MIS" AgentVersion="1.0" 
                    Time="2016-05-30T21:49:47Z" />
        </AuditCreated>
    </AuditPool>
    <ProductList>
        <Product Amount="2500" DescriptiveName="My Folded Leaflet">
            <Intent Name="LayoutIntent">
                <LayoutIntent Dimensions="841.88 595.27" 
                        Sides="TwoSidedHeadToHead" Pages="2"
                        FinishedDimensions="280.69 595.27 0.0"/>
            </Intent>
            <Intent Name="FoldingIntent">
                <FoldingIntent FoldCatalog="F6-2"/>
            </Intent>
            <Intent Name="ColorIntent">
                <ColorIntent>
                    <SurfaceColor Surface="Front"
                            ColorsUsed="Cyan Magenta Yellow Black"/>
                    <SurfaceColor Surface="Back" 
                            ColorsUsed="Cyan Magenta Yellow Black" />
                </ColorIntent>
            </Intent>
            <Intent Name="MediaIntent">
                <MediaIntent MediaQuality="135_MATT"/>
            </Intent>
        </Product>
    </ProductList>
    <ResourceSet Name="Component" Usage="Input">
        <Resource ExternalID="COMP_ID_UNFOLDED">
            <Component Dimensions="841.88 595.27 0.42" 
                    MediaRef="MEDIA-ID" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="Component" Usage="Output">
        <Resource ExternalID="COMP_ID_FOLDED">
            <AmountPool>
                <PartAmount Amount="2580" />
            </AmountPool>
            <Component Dimensions="280.69 595.27 1.26" 
                    MediaRef="MEDIA-ID" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="FoldingParams" Usage="Input">
        <Resource>
            <FoldingParams FoldCatalog="F6-2"/>
        </Resource>
    </ResourceSet>
    <ResourceSet Name="Media">
        <Resource ID="MEDIA-ID">
            <Media MediaType="Paper" Thickness="150" Weight="135" 
                    ISOPaperSubstrate="PS3" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="NodeInfo" Usage="Input">
        <Resource>
            <NodeInfo Start="2016-08-30T15:00:00Z" />
        </Resource>
    </ResourceSet>
</XJDF>
```

The XJDF example begins with the XJDF root node. In the root node there is an attribute `@JobID` specifying the job’s unique identifier and an attribute `@Types` which defines the Gray Box of the device the XJDF is addressed to. The AuditPool element keeps the metadata of the creator of the document, as well as the timestamp of the creation.

The ProductList element contains only one Product element which describes the final product. The final product consists of 2,500 6-panel folded leaflets printed in four colors, double sided on 135 gsm matt paper. All features of the desired product are defined as Intent elements. 

The LayoutIntent defines the open (unfolded) size of the folded leaflet (`@Dimensions`) as well as closed (folded) size (`@FinishedDimensions`). The sizes are defined in units of “desktop publishing points” (dtp). More details about dtp are presented later in the section “Measurements, Units, and Data Types”. The attribute `@Sides` defines the orientation of the front page against the back page. The value “TwoSidedHeadToHead” means that, when turning the product sideways, it remains in the reader's orientation.
FoldingIntent defines how the product has to be folded. The exact fold is defined by the XJDF fold catalog (`@FoldCatalog`). The attribute value “F6-2” defines a 6-panel zig-zag-fold as shown below:

<figure>
  <Image src={f62} alt="Sketch of a F6-2 fold" />
  <figcaption>Figure: Sketch of a F6-2 fold</figcaption>
</figure>

The XJDF fold catalog defines a set of various standardized folding schemes. More details about the fold catalog will be revealed later. 
The ColorIntent specifies that the product has to printed using the four process colors Cyan, Magenta, Yellow and Black (CMYK) on both sides. MediaIntent defines a 135 gsm substrate of matt paper for the product. 

As previously mentioned, Product elements define the customer's perspective of the desired product. Product descriptions are process independent. Process relevant data has to be defined as resources. This XJDF folding example contains the resources Component, FoldingParams, Media, and NodeInfo.

“Component is used to describe the various versions of semi-finished goods in the press and postpress area, such as a pile of folded sheets that have been collected and are then be joined and trimmed. Nearly every postpress process has a Component resource as an input as well as an output. Typically the first components in the process chain are some printed sheets or ribbons, while the last Component is a book or a brochure” [@xjdf_ip1, chap. 6.18 "Component"]. The folding process consumes a flat sheet as input (`//ResourceSet/@Usage=”Input”`) and produces a folded sheet as output (`//ResourceSet/@Usage=”Output”`). The output Component resource also contains an element AmountPool which is a container for the amount-related metadata. In this example it defines the production of 2,580 copies of the folded leaflets as a result of the folding process (eighty copies more than what was required in the customer order).

A further input of the folding process is the FoldingParams resource. The FoldingParams “describes the folding parameters, including the sequence of folding steps” [@xjdf_ip1, chap. 6.37 "FoldingParams"]. They describe the digital fold settings of the job. In this example, these settings are quite similar to those previously defined in the FoldingIntent element. There is only a reference to the “F6-2” folding scheme of the XJDF fold catalog. 

A Media resource “represents the properties of a raw, unexposed printable surface such as sheet, film or plate” [@xjdf_ip1, chap. 6.58 "Media"]. In this context, Media describes paper (`@MediaType`=”Paper”). In contrast to the MediaIntent, the Media resource defines the paper in quite a bit more detail. Media is not a direct input or output resource of the folding process. Instead, the Media resource is referenced by the two Components using ID / IDRefs (see `//Component/@MediaRef=”MEDIA-ID”` and
`//ResourceSet[@Name=’Media’]/Resource/@ID=”MEDIA-ID”`) in order to get more information on the component’s paper such as weight, type, etc. Therefore, the Media resource is the only resource with an attribute `@ID` in the example.

The last resource in the XJDF example is the input resource NodeInfo. “The NodeInfo Resource contains information about planned scheduling. It allows MIS systems to plan, schedule and invoice Jobs or Job Parts” [@xjdf_ip1, chap. 6.60 "NodeInfo"].


## Resources
“Resource elements are child elements of a ResourceSet and describe the physical or logical entity in the partition context [...]. For instance a `ResourceSet/@Name`="ExposedMedia" can specify a set of printing plates and each child Resource element will describe an individual plate” [@xjdf_ip1, chap. 6.1 "Resource"]. Resources are usually associated with a specific process, but they can also be associated with Products. Each Resource element is part of a specific ResourceSet. A “ResourceSet describes a set of one or more Resource elements that are logically grouped together” [@xjdf_ip1, chap. 3.3 "ResourceSet"]. 
The following example shows a simple RunList resource as an illustration of the fundamental XML structure of resources:

```xml title="Example: RunList Resource"
[...]
<ResourceSet Name="RunList" Usage="Input" >
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/artwork/my.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
[...]
```

“A RunList defines one or more printable logical documents or document sets that MAY be defined in one or more external [...] files” [@xjdf_ip1, chap. 6.73 "RunList"]. A RunList is mainly used in prepress processes as well as in web-to-print scenarios, in order to reference the customer artworks or other digital data to be processed. The RunList in the example above has a FileSpec subelement which references a file using an URL.

The RunList element is a subelement of Resource and the Resource element is a subelement of ResourceSet. Even when just a single Resource element has to be specified, the whole element’s structure has to be declared. At first glance, this may appear to be over-engineered, but having a unique, stable and extensible structure is essential for the quality and long-term stability of a data format. This structure guarantees simplicity for simple use cases but can also describe complex scenarios by simply extending the XJDF elements with additional attributes. 

The attribute `//ResourceSet/@Name` is required for each ResourceSet element and “specify the name of the explicit resource that this ResourceSet represents. Child resource elements of this ResourceSet SHALL NOT contain resources that do not match `@Name`” [@xjdf_ip1, chap. 3 Table 3.4: ResourceSet/@Name]. 
The attribute `//ResourceSet/@Usage` defines the usage of the ResourceSet within the XJDF Document. Valid values are “Input” and “Output”. The value “Input” defining the ResourceSet is an input resource of the Gray Box, whereas the value “Output” specifies that the ResourceSet has to be produced as output by the Gray Box. In some cases, ResourceSets may contain Resources which are neither input nor output of processes. Resources can also be linked to resources such as the Media resource in the Folding Example above. In that case, the attribute `//ResourceSet/@Usage` doesn’t need to be written. The following is an extract of the appropriate part in the Folding Example:

```xml title="Example: Extract Folding Example - References of Resources"
[...]
<ResourceSet Name="Component" Usage="Input">
    <Resource ExternalID="COMP_ID_UNFOLDED">
        <Component Dimensions="841.88 595.27 0.42" 
            MediaRef="MEDIA-ID" />
    </Resource>
</ResourceSet>
<ResourceSet Name="Component" Usage="Output">
    <Resource ExternalID="COMP_ID_FOLDED">
        <Component Dimensions="280.69 595.27 1.26"
            MediaRef="MEDIA-ID" />
    </Resource>
</ResourceSet>
[...]
<ResourceSet Name="Media">
    <Resource ID="MEDIA-ID">
        <Media MediaType="Paper" Thickness="150" Weight="135" 
            ISOPaperSubstrate="PS3" />
    </Resource>
</ResourceSet>
[...]
```

In this extract of the folding example there are three ResourceSet elements. Each ResourceSet element contains an individual Resource element. The upper two ResourceSet elements describe the input and the output components of the folding process (see attribute `//ResourceSet/@Usage`), whereas the lower one specifies details about the paper substrate (Media). The lower ResourceSet “Media” does not contain any `@Usage` attribute at all. Media is neither an input nor an output resource of folding directly, but it is linked by the two Component resources in order to specify details about the paper substrate. The Media can be referenced by its unique ID “MEDIA-ID”. The identifier of the Media resource is NOT an attribute of the Media element directly, but rather an attribute of the generic Resource element (see `//Resource/@ID` equals “MEDIA-ID”). Both Component resources are linking the Media via the attribute `//Component/@MediaRef` = “MEDIA-ID”.

### Partitioning of Resources
When describing a logical set of resources in a ResourceSet, XJDF provides a partitioning mechanism for the purpose of identifying the appropriate resource. Partitioning defines the context in which the individual resource element is used. The following example outlines a RunList of a customer’s artwork, separated into two files, one per side:

```xml title="Example: RunList Resource Partitioned by Side"
[...]
<ResourceSet Name="RunList">
    <Resource>
        <Part Side="Front" />
        <RunList>
            <FileSpec URL="http://example.org/files/my-page-1.pdf"/>
        </RunList>
    </Resource>
    <Resource>
        <Part Side="Back" />
        <RunList>
            <FileSpec URL="http://example.org/files/my-page-2.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
[...]
```

In addition to the specific resource element, there is a second subelement “Part” in the Resource element. The Part element is the key element for the partitioning of resources. “The Part elements identify the partition context of the Resource element” [@xjdf_ip1, chap. 6 Table 6.1: Resource/Part]. In the example above, the RunList resources are partitioned by `@Side`. The attribute `//Part/@Side` “denotes the side of the Sheet” [@xjdf_ip1, chap. 6 Table 6.6: Part/Side]. The upper RunList resource in the example references the file of the front page (`//Part/@Side = ”Front”`), while the lower RunList resource references the back page (`//Part/@Side = ”Back”`).
The chronology of the sub-elements in element `//Resource` is given by the XJDF Specification. If it exists, the Part element has to be the first element within the Resource element.

Partitioning is not a standard XML mechanism but rather a singularity of XJDF. “Part elements define the context in which the individual Resource is used. Resource partitions are uniquely identified by the Resource/Part elements” [@xjdf_ip1, chap. 6.1.5 "Part"]. Partitioning has been introduced in order to simplify the structure of resources. In XJDF, only resources can be partitioned. 
As Part is the key element for partitioning, its attributes define how resources can be partitioned. Therefore, these attributes are also known as “Partition Keys”. Further examples of partition keys include `@ProductPart`, `@Separation`, and `@PartVersion`. 
The partition key `@ProductPart` “references the `//Product/@ID` that this Part applies to” [@xjdf_ip1, chap. 6 Table 6.6: Part/ProductPart] (product intent). The key `@Separation` “identifies a color separation” [@xjdf_ip1, chap. 6 Table 6.6: Part/Separation] such as “Cyan”, “Magenta”, “Yellow”, “Black” and `@PartVersion` is a “Version identifier (e.g., the language version of a catalog)” [@xjdf_ip1, chap. 6 Table 6.6: Part/ProductVersion]. The full list of all valid partition keys can be found in the XJDF Specification in the chapter “6.1.5 Part”. 

Below is an example using the partition key `@Separation` as a means of defining the logical group of four printing plates required by a four colored printing job. Each printing plate applies to a different separation (Cyan, Magenta, Yellow, Black), but logically, they are in the same group of resources. Technically, each printing plate is expressed by an individual ExposedMedia resource, but all four resources are sub-elements of the same ResourceSet:

```xml title="Example: Extract of ResourceSets of a ConventionalPrinting XJDF"
<XJDF JobID="JOB-42" Types="ConventionalPrinting"
      xmlns="http://www.CIP4.org/JDFSchema_2_0">
   [...]
   <ResourceSet Name="ExposedMedia" Usage="Input" ProcessUsage="Plate">
       <Resource>
           <Part Separation="Cyan"/>
           <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
       </Resource>
       <Resource>
           <Part Separation="Magenta"/>
           <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
       </Resource>
       <Resource>
           <Part Separation="Yellow"/>
           <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
       </Resource>
       <Resource>
           <Part Separation="Black"/>
           <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
       </Resource>
   </ResourceSet>
   [...]
</XJDF>
```

The ResourceSet in the example above is of type “ExposedMedia” and contains the four printing plates - one per color separation. All ExposedMedia resources are partitioned by the partition key “Separation”. Each resource can therefore be assigned to its respective separation.

A Part element may also define multiple partition keys, and a Resource element may even contain multiple Part elements. “If multiple Part elements are specified within one Resource, the Resource specifies one entity that applies to both parts” [@xjdf_ip1, chap. 6.1.5 "Part"]. Here: an example with two language versions where both scenarios occur:

```xml title="Example: Multiple Part elements per Resource"
[...]
<ResourceSet Name="ExposedMedia">
    <Resource>
        <Part Separation="Cyan" PartVersion="German" />
        <Part Separation="Cyan" PartVersion="English" />
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" />
    </Resource>
    <Resource>
        <Part Separation="Magenta" PartVersion="German" />
        <Part Separation="Magenta" PartVersion="English" />
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" />
    </Resource>
    <Resource>
        <Part Separation="Yellow" PartVersion="German" />
        <Part Separation="Yellow" PartVersion="English" />
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" />
    </Resource>
    <Resource>
        <Part Separation="Black" PartVersion="German" />
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" />
    </Resource>
    <Resource>
        <Part Separation="Black" PartVersion="English" />
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" />
    </Resource>
</ResourceSet>

<ResourceSet Name="Media">
    <Resource ID="MEDIA-PLATE-ID">
        <Media MediaType="Plate" />
    </Resource>
</ResourceSet>
[...]
```

This partitioning example describes a set of five printing plates (ExposedMedia) of a language versioned print job. The printing plates of the separations Cyan, Magenta, and Yellow are the same for both versions (“German” and “English”), while the separation Black is individual per version. Two Part elements imply that this printing plate is being used in both print runs (“German” and “English”).

This versioning method in printing assumes that all the versioning of the print product is being done in the Black separation only. The color separations (Cyan, Magenta and Yellow) are equal in both versions. The consumption of three plates, as well as the corresponding make-ready time, can therefore be saved in order to reduce the production costs.


## Extensibility
The XJDF Specification allows several methods for extending the data format. However, the extensions must not duplicate the functionality which is defined in XJDF. As XJDF is a holistic approach in the graphic arts industry, it is strongly recommended to use the standard elements and attributes as much as possible instead of introducing new private extensions. The XJDF Specification has grown based on extensive expert discussions across different system vendors, consultants and users for quite some time. The outcome of these discussions is this structure as described in the specification. The structure ensures long-term stability and extensibility simultaneously. In some cases, the introduction of new custom extension may appear as a shortcut or even as a simplification. However, private tags may harm the long-term stability and extensibility of an XJDF Interface. 

**When missing functionality, the preferred way is to start a new discussion in the CIP4s issue tracking system (JIRA) (see chapter “Authoring Process”). The result of the discussion is either a solution of how to resolve the request using the current standard methods, or an extension or modification of the specification for the next version of XJDF. Within the interim period, private namespaces can be used.**

“Attributes in a foreign namespace MAY be added to any XJDF element. Elements in a foreign namespace SHALL NOT be specified in XJDF elements other than Notification, Resource and Intent elements” [@xjdf_ip1, chap. 3.5.1 "Foreign Namespaces"]. Therefore, XJDF provides the following methods for extending the data format:

* Custom intents and resources
* Custom processes
* Custom values in NMTOKEN lists.
* Custom notifications

When working with private namespaces it is recommended to have only one namespace URI and only one standardized prefix per company. Once introduced, neither the namespace URI nor the prefix should be changed. “Elements in a foreign namespace SHALL be specified after any elements in the XJDF namespace” [@xjdf_ip1, chap. 3.5.1 "Foreign Namespaces"].

### Custom Intents and Resources
XJDF provides the ability to extend the data format by new private intents and resources. The following example illustrates how to add a custom resource:

```xml title="Example: Custom Resources"
<XJDF Types="ProcessName" JobID="5" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0"
        xmlns:foo="http://example.org/foo">
    [...]
    <ResourceSet Name="foo:bar">
        <Resource>
            <foo:bar attribute="myAttributeValue" />
        </Resource>
    </ResourceSet>
    [...]
</XJDF>
```

In the first step, a new foreign namespace has been introduced in the XJDF root node. In this case, this namespace URI is *"http://example.org/foo”* and is prefixed by “foo”. The new custom specific resource element is a subelement of Resource. The full name of the element (including the prefix) is the value of the `@Name` attribute in ResourceSet.

The introduction of a new custom intent element is quite similar to the introduction of a custom resource. The following is an example as an illustration:

```xml title="Example: Custom Intents"
<XJDF Types="ProcessName" JobID="5" 
        xmlns="http://www.CIP4.org/JDFSchema_2_0"
        xmlns:foo="http://example.org/foo">
    [...]
    <ProductList>
        <Product>
            <Intent Name="foo:bar">
                <foo:bar attribute="myAttributeValue" />
            </Intent>
        </Product>
    </ProductList>
    [...]
</XJDF>
```

### Custom Processes
Processes can also be extended in XJDF. “XJDF defines a basic set of process types. However, because XJDF allows flexible encoding, this list, by definition, will not be complete. Vendors that have specific processes that do not fit in the general XJDF processes and that are not combinations of individual XJDF processes [...] can create process XJDF of their own type” [@xjdf_ip1, chap. 3.5.5 "Extending Process Types"].

The company's standardized namespace URI and prefix should be written in the XJDF root element. In order to introduce the new process, the process’s name, including the company’s prefix, has to be written in the `@Types` attribute. Both values have to be separated by a colon (“:”). 


### Custom Values in NMTOKEN lists
“Many Resources contain attributes of type NMTOKEN and some of these have a set of predefined, suggested enumerative values. These lists MAY be extended with private keywords” [@xjdf_ip1, chap. 3.5.4 "Extending NMTOKEN Lists"].

```xml title="Example: Custom NMTOKEN Values"
<XJDF Types="ProcessName" JobID="5"
    xmlns="http://www.CIP4.org/JDFSchema_2_0" >
    [...]
    <ProductList>
        <Product Amount="250">
            <Intent Name="ColorIntent">
                <FoldingIntent FoldCatalog="F6-MY-FOLD" />
            </Intent>
            [...]
        </Product>
    </ProductList>
    [...]
</XJDF>
```

As `@FoldCatalog` attributes are of type NMTOKEN, they can be extended by new values. This example shows the introduction of a new custom fold scheme “F6-MY-FOLD”. When extending NMTOKEN lists by custom values, no custom namespace declaration is required. 


### Custom Notifications
Notifications are another element which can be extended by custom subelements. More details about custom notifications can be found in the specification.


## Identifiers
The XJDF Specification defines several types of identifiers (IDs) in order to identify resources, jobs, devices etc. This section gives a brief introduction to the most important IDs, what they are responsible for, and their appropriate scope. An identifier has to be unique within its scope. For instance, the scope “Production” means the identifier has to be unique within the whole production system. A production system may cover several sites. The following table contains the most significant XJDF IDs:

| ID Name | Description | Scope | Example |
| ------- | ----------- | ----- | ------- |
| `ExternalID` | Unique identifiers of physical resources. | Production | `COMP-34` |  
| `ID` / `IDRef` | Unique identifiers and references within a single XJDF Document | Document | `j3hduw83` |
| `Partition Key` | Unique identifier of a specific partition. | Production | `SHEET-1` |
| `JobID` | Unique identifier of a job. | Production | `JB-124` |
| `JobPartID` | Identifies one or more worksteps of the same type | Production | `Front` |
| `DeviceID` | Unique identifier of a device. | Production | `PRESS-1` |


### ExternalID
The `@ExternalID` is “an ID of the resource as defined in the MIS system. For instance item codes or article numbers or identifiers on semi-finished products or Resource elements. `@ExternalID` shall be used to uniquely identify resources and products for the purpose of inventory tracking” [@xjdf_ip1, chap. 6 Table 6.1: Resource/ExternalID].
Generally, each resource can be assigned by an item code, article number, or identifiers. An ExternalID has to be unique within a whole production system. Once defined, the resource’s ExternalID should not be changed.

```xml title="Example: ExternalID in Resources"
[...]
<ResourceSet Name="Component" Usage="Input">
    <Resource ExternalID="COMP_ID_UNFOLDED">
        <Component Dimensions="841.88 595.27 0.42"
            MediaRef="MEDIA-ID"/>
    </Resource>
</ResourceSet>
<ResourceSet Name="Component" Usage="Output">
    <Resource ExternalID="COMP_ID_FOLDED">
        <Component Dimensions="280.69 595.27 1.26"
            MediaRef="MEDIA-ID"/>
    </Resource>
</ResourceSet>
[...]
```

This example is an extract of the Folding Example and shows two ResourceSet elements, each containing a Component Resource. Both Resource elements describe semi-finished goods. The upper one is the description of the unfolded sheet as input resource, whereas the lower one refers to the specification of the folded sheet as the output resource of the folding process. Both resources are identified by an individual `@ExternalID` attribute. The input resource is identified by `@ExternalID = "COMP_ID_UNFOLDED”` and the output resource is identified by `@ExternalID = "COM_ID_FOLDED"`. Both identifiers identify the appropriate resources during their lifecycle. During the folding process, the lifecycle of the component `COMP_ID_UNFOLDED` ends, while the lifecycle of `COMP_ID_FOLDED` begins.
In a real-world scenario, the ExternalID may be printed out on a label and stuck on the component’s pile for identification. This enables users to easily identify the individual components in the warehouse. 


### ID / IDRef
ID / IDRef attributes are for internal document references only. The values of these attributes may change from one transaction to the next. ID / IDRefs must not be used to identify resources within the production workflow. Valid locations for IDs are the attributes `//ResourceSet/@ID` and `//Resource/@ID`. 
“Unless otherwise specified, an `@IDREF` or `@IDREFS` will refer to an individual Resource rather than an entire ResourceSet” [@xjdf_ip1, chap. 3.3 "ResourceSet"].

```xml title="Example: Internal document reference using ID / IDRef"
[...]
<ResourceSet Name="Component" Usage="Output">
    <Resource ExternalID="COMP_ID_FOLDED">
        <Component Dimensions="280.69 595.27 1.26" 
            MediaRef="MEDIA-ID" />
    </Resource>
</ResourceSet>
[...]
<ResourceSet Name="Media">
    <Resource ID="MEDIA-ID">
        <Media MediaType="Paper" Thickness="150" Weight="135" 
            ISOPaperSubstrate="PS3" />
    </Resource>
</ResourceSet>
[...]
```

This example is also an extract of the Folding Example. The first ResourceSet contains a Component resource and the second one a Media resource. The Media resource is referenced by the Components `@MediaRef` attribute. The value of the attribute `//Component/@MediaRef` is equals to the ID value of the Media Resource (see `//ResourceSet/Resource/@ID`). This reference is used to obtain additional information about the paper of the component.

The `MEDIA-ID` is NOT the global identifier of the paper or pile in the company. The IDs value is for internal document references only and may change from one transaction to the next. A global media identifier would have to be written as the value of the `@ExternalID` attribute. 


### Partition Key
Whenever a ResourceSet contains several Resource elements which are NOT referenced using ID / IDRefs, the subselection of the appropriate resources is based on partitioning. Partitioning is an XJDF specific mechanism and is explained in the section “Resources”.
Partition keys are called the attributes of the Part element. In contrast to ExternalIDs and the ID / IDRefs references, the values of these attributes are normally given by the specification.

```xml title="Example: Selection by Partition Keys"
[...]
<ResourceSet Name="ExposedMedia" Usage="Input" ProcessUsage="Plate">
    <Resource>
        <Part Separation="Cyan"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Magenta"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Yellow"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Black"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
</ResourceSet>
[...]
```

The example above has already been shown in the Resources section and outlines an ResourceSet ExposedMedia containing four different kinds of ExposedMedia resources. All four items are distinguished by their Partition Key `@Separation` (Cyan, Magenta, Yellow and Black). 

The values of the partition key `@Separation` are given by the specification:

  <Image src={screenPartSeparation} alt="The Definition of the Separation Partition Key (XJDF Spec Extract)" />
  <figcaption>Figure: The Definition of the Separation Partition Key (XJDF Spec Extract)</figcaption>

Among others, there is one value specified per color separation. The data type of the partition key `@Separation` is “NMTOKEN”. This indicates that the partition key is an open list. The specification defines a standard set of the most common values, but each vendor is free to add additional values (see the section “Extensibility”).


### JobID, JobPartID, DeviceID...
Apart from the identifiers mentioned above, XJDF comes with a huge bunch of identifiers for many different applications. The usages of these IDs are explained in the specification and do not require additional explanations. The IDs - JobID, JobPartID, and the DeviceID - which are frequently used in XJDF, are explained in the following paragraph.

The JobID is the “Job identification used by the application that created the XJDF Job. Typically, a Job is identified by the internal order number of the MIS system that created the Job” [@xjdf_ip1, chap. 3 Table 3.1: XJDF/JobID]. An example value would be “674R834”. A JobID has to be unique within a production workflow and should not be changed once it has been defined.
The ”JobPartID SHALL identify one or more worksteps of the same type that can be described as one XJDF. `@JobPartID` is internal to the MIS system that created the XJDF” [@xjdf_ip1, chap. 3 Table 3.1: XJDF/JobPartID]. Example values are “Front” and “Back”.
The DeviceID is the “identifier of the Device. The `@DeviceID` SHALL be unique within the workflow. `@DeviceID` SHALL be the same over time for a specific Device instance (i.e., SHALL survive reboots)” [@xjdf_ip1, chap. 6 Table 6.58: Device/DeviceID]. A example value would be “SM-162-8”.

The explanations of all three identifiers are successively taken from the XJDF Specification. The specification defines the exact purpose of an ID, its data type, as well as the scope of the identifier. “The word ‘Unique’ without further scope details means ‘Unique within the job, message or file depending on the context’” [@xjdf_ip1, chap. 1 Table 1.4: Glossay (Unique)].


## Measurements, Units, and Data Types
“XJDF specifies most values in default units. That means that an implementation SHALL use the defined default units and SHALL NOT use alternate units [...]. Processors SHOULD NOT specify a unit unless no default exists, such as when new resources are defined. Then the units SHALL be based on metric units. Overriding the default units that are defined [...] is non-standard and MAY lead to undefined behavior. Any exceptions are specified in the appropriate descriptive tables” [@xjdf_ip1, chap. 1.9.1 "Units"]. All default units, their representation, and related remarks can be found in the XJDF Specification in chapter 1.9.1, Units.

The most significant measurement in XJDF is the length. With the exception of microscopic lengths, all length values are defined in desktop publishing points (dtp points). Examples are width, height, dimensions, positions, etc. A point is defined as 1/72nd of an inch. The following gives instructions on the conversion of millimeters to points and vice versa:

```java title="Conversion dtp points (dtp) to millimeter (mm) and vice versa"
// Conversion dtp points (dtp) to millimeter (mm)
mm = dtp * 72.0 / 25.4 

// Conversion millimeter (mm) to dtp points (dtp)
dtp = mm * 25.4 / 72.0 
```

Length values are used in various data structures, depending on the particular case they are used in. This table is an excerpt of common XJDF data types which are relevant with respect to  length expressions:

| Data Type | Description | Example |
| --------- | ----------- | ------- |
| `float` | A float is a single value expression as used for width or height expressions. | `"595.27"` |
| `rectangle` | Attributes of type rectangle are used to describe rectangular locations on the page, Sheet or other printable surface. A rectangle is represented as an array of four float numbers - llx lly urx ury - specifying the lower-left x, lower-left y, upper-right x and upper-right y coordinates of the rectangle, in that order. The origin for positioning is always the lower left corner of the parent object. | `"10.0 10.0 290.69 605.27"` |
| `shape` | A shape is represented as an array of three (positive or zero) float numbers - x y z - specifying the width x, height y and depth z coordinates of the shape, in that order. A shape is typically used for three-dimensional objects such as a book block. | `"280.69 595.27 1.26"` |
| `XYPair` | Attributes of type XYPair are mainly used to describe sizes like `@Dimensions` [...]. They can also be used to describe positions on a page. An XYPair is typically used for two-dimensional definitions such as page size. | `"290.69 605.27"` |


The table is an excerpt of data types as defined in the XJDF Specification whose relevance pertains to lengths. A data type is defined for each attribute in the specification. The following is an extract of the Folding example which contains some length expressions:

```xml title="Example: Common data types which are relevant in combination with lengths"
[...]
<ResourceSet Name="ExposedMedia" Usage="Input" ProcessUsage="Plate">
    <Resource>
        <Part Separation="Cyan"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Magenta"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Yellow"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
    <Resource>
        <Part Separation="Black"/>
        <ExposedMedia MediaRef="MEDIA-PLATE-ID" PlateType="Exposed" />
    </Resource>
</ResourceSet>
[...]
```

In the upper example, there are three attributes containing length related expressions. ## Folding Schemes and Pagination
Folding and pagination are major tasks in a print production. Folding describes how a sheet or a final product has to be folded (e. g. zig-zag fold) and pagination defines how the single pages have to be ordered and positioned. Both are closely related, as folding schemes have a major effect on the positioning and orientation of pages on a sheet. 

In XJDF, each print product is described as a set of one or multiple product parts. A simple flyer or a folded leaflet consists of just one single product part, whereas a complex product consists of at least two or even more product parts. The following drawing outlines the product parts of a brochure containing 24 pages with two different types of papers - one for the cover and one for the body. Therefore, the brochure consists of the two product parts “Cover” and “Body”. The cover has four pages and is printed on premium paper, whereas the body consists of 20 pages and is printed on a more common type of paper:

<figure>
  <Image src={diagramBrochureProductParts} alt="Product parts of a softcover-brochure" />
  <figcaption>Figure: Product parts of a softcover-brochure</figcaption>
</figure>

In order to produce the desired print product, each product part has to be separated into one or several bindery signatures. “A BinderySignature represents both sides of a folding signature, a die cut surface or a flat product such as a postcard, each with one or more pages” [@xjdf_ip1, chap. 6.6 "BinderySignature"]. Each bindery signature is defined by a specific folding scheme. The exact distribution of the product parts in bindery signatures depends on the machinery of the appropriate printing house and the exact production plan of how the brochure is intended to be produced. 

Note: The bindery signature is only the logical description of how to fold and how to position the single pages on a component. Each logical bindery signature is related to a physical component in the production process. Components specify “the various versions of semi-finished goods in the press and postpress area, such as a pile of folded sheets that have been collected and are then be joined and trimmed” [@xjdf_ip1, chap. 6.18 "Component"]. 

A brochure with sixteen pages and only one product part can be separated into either a 16-page bindery signature, two 8-page bindery signatures, or into four 4-page bindery signatures. Combinations thereof are also permissible. The production plan is automatically calculated by the Management Information System, or manually by a production operator for the purpose of determining the most efficient production plan. 
The brochure in the example above may be separated into three bindery signatures. A 4-page bindery signature for the cover, and both a 16-page and a 4-page bindery signature for the body. The exact type of the bindery signatures is defined by the `@FoldCatalog` identifier. More about the `@FoldCatalog` identifiers and their respective meanings later in this section. The following is a drawing which outlines the bindery signatures and their corresponding folding scheme for the example brochure:

<figure>
  <Image src={diagramBrochureBsOverview} alt="Example of BinderySignatures for a softcover-brochure" />
  <figcaption>Figure: Example of BinderySignatures for a softcover-brochure</figcaption>
</figure>

The first bindery signature on the left (gray) represents the cover of the brochure. This bindery signature has four pages and contains the first and the last two pages. The largest bindery signature is the second one. This one contains sixteen pages of the body (pages 3 to 10 and 15 to 22). The pages are positioned in two rows and four columns. Because of folding, all pages in the lower row are rotated by 180 degrees. The third bindery signature on the right has four pages and contains the center pages (pages 11 to 14).
Each component, described by a BinderySignature element, is printed and folded individually. In order to produce the final product, the three components are assembled and stitched together:

<figure>
  <Image src={diagramBrochureGathering} alt="Collecting of Components for a Softcover-Brochure" />
  <figcaption>Figure: Collecting of Components for a Softcover-Brochure</figcaption>
</figure>

The distribution, positioning and orientation of the single pages on the different components is crucial. Pagination determines “the distribution and orientation of pages on a BinderySignature [...]" [@xjdf_ip1, chap. 5.4.22.1 "Pagination in Stripping"].
The pagination depends on the finishing process, that is, the planning for how the final product will be produced. It depends on the number, size, and types of bindery signatures, as well as on how the individual bindery signatures are supposed to be bound (collecting or gathering). Collecting means that the bindery signatures are collected on a spine and are placed within one another. The first bindery signature is on the outside of the final product (as shown in the example). Gathering is the alternative method of assembling. When gathering, all bindery signatures are gathered on a pile and placed on top of one another so that the first one is on the top of the final product. This method is used for non stitching binding types.

A bindery signature is conceptually the smallest physical component in which all print products have to be separated. Even a simple two-sided flyer has to be described as an F2-1 bindery signature. Therefore, bindery signatures play a major role in a print production workflow. At a minimum, a bindery signature is defined by its FoldCatalog attribute value and the partition key `@BinderySignatureID`. 

```xml title="Example: A BinderySignature ResourceSet"
[...]
<ResourceSet Name="BinderySignature" Usage="Input">
    <Resource>
        <Part BinderySignatureID="BS-1" ProductPart="COVER-ID" />
        <BinderySignature FoldCatalog="F4-1"/>
    </Resource>
    <Resource>
        <Part BinderySignatureID="BS-2" ProductPart="BODY-ID" />
        <BinderySignature FoldCatalog="F16-7"/>
    </Resource>
    <Resource>
        <Part BinderySignatureID="BS-3" ProductPart="BODY-ID" />
        <BinderySignature FoldCatalog="F4-1"/>
    </Resource>
</ResourceSet>
[...]
```
This snippet is an extract of the XJDF Collecting example to be presented later and can be analyzed in detail at that point. The relevant details here are the `@BinderySignatureID` partition key, the `@FoldCatalog` attribute, and the XML element structure.
The `@BinderySignatureID` partition key is the “master identifier of a BinderySignature” [@xjdf_ip1, chap. 6 Table 6.6 Part/BinderySignatureID] within the production workflow. The value of the `@FoldCatalog` attribute is a fold catalog identifier which refers to a predefined standard fold scheme in the XJDF fold catalog. The format of the fold catalog identifier is “‘Fn-i’ where ‘n’ is the number of finished pages and ‘i’ is either an integer, which identifies a particular fold or the letter ‘X’ which identifies a generic fold” [@xjdf_ip1, chap. A.3.3 "Fold Catalogs"]. 

In the following illustration, an extract of the XJDF fold catalog which describes the most common fold schemes is depicted. These fold schemes are predefined in many JDF and XJDF enabled applications and devices, such as imposition software and folding machines. The method of interpreting the XJDF fold catalog is discussed below.

The first part of the identifier (“F18”) indicates that the folding scheme produces eighteen finished pages. The number six in the fold catalog identifier is a sequential number within the “F18” - group.
The term “3x3” denotes the positioning of the pages on a sheet when using the folding scheme. This value is just for information purposes and provides an initial orientation in order to facilitate finding folding schemes more quickly. “3x3” means there are three by three pages.

Arrow up (⬆) means the left section has to be folded over the right section or the bottom section has to be folded over the top section. Arrow down (⬇) indicates that the left section has to be folded under the right section or the bottom section has to be folded under the top section. The size of the appropriate section is expressed by a fraction of the open sheet size. Fractions of horizontal folds refer to the width of the open sheet, while vertical folds refer to the height. The first fold is always a horizontal fold. The plus sign ( + ) is used to toggle between the horizontal and the vertical folds.
The XJDF fold catalog provides folding schemes for the most standard situations in a print production workflow. In the event that there is no match, XJDF provides generic fold schemes. An example of a generic 18-pages bindery signature would be “F18-X”. 
Custom folds are also supported. The procedure for extending the XJDF by a custom folding scheme is explained in the section “Extensibility”. However, the disadvantage of both methods is that they pose limitations on automation. 

### XJDF Example: Collecting
Many collecting devices do not only collect pre-folded components, but also provide stitching and trimming. The input of such machines is a set of pre-folded bindery signature components, while the output is a finished brochure.

From the XJDF perspective, such devices are described by a Gray Box covering the processes Collecting, Stitching, and Trimming. The process Collecting “collects folded sheets or partial products[...]. The first component to enter the workflow lies at the bottom of the pile collected on a saddle, and the sequence of the input components that follows depends upon the produced component” [@xjdf_ip1, chap. 5.6.7 "Collecting"]. The process Stitching defines how “gathered or collected sheets or signatures are stitched together” [@xjdf_ip1, chap. 5.6.33 "Stitching"]. After collecting and stitching, the semi-finished magazines have to be trimmed on the head, the foot, and the face. This is done by the Trimming process. “The Trimming process is performed to adjust a book block or sheet to its final size” [@xjdf_ip1, chap. 5.6.37 "Trimming"].
The following example illustrates an XJDF Document describing a “Collecting Stitching Trimming” Gray Box:

The collecting example is quite similar to the folding example. One difference here is that the ProductList describes a complex product as opposed to a simple one. The complex product consists of a root product and two child products. The root product describes the overall brochure, whereas the two child products describe both product parts of the brochure - cover and body. More about complex products will be explained in the next chapter.
Since a collecting device provides more processes than a simple folding machine, the number of input resources is higher. The primary resources of interest here are Assembly and BinderySignature. As defined, the magazine has been separated into three bindery signatures. A four-page bindery signature for the cover and two bindery signatures (16 and 4 pages respectively) for the body. Using the `@ProductPart` partition key, each BinderySignature element references a child product. The Assembly element defines how the single bindery signatures have to be assembled in order to obtain the final product. The attribute `@BinderySignatureIDs` refers to the bindery signatures to be assembled. The order of the IDs within the attribute corresponds to the order in which all bindery signatures are to be assembled. The attribute `@Order` = “Collecting” defines the first ID mentioned and is the outer component, while the following ones are bonded within one another (see the figure “Collecting of BinderySignatures for a softcover-brochure”).
Each BinderySignature element of the magazine is linked to a Component using the `@BinderySignatureID` partition key. A component is the physical representation of a bindery signature.
StitchingParams and TrimmingParams are specific input resources for the processes Stitching and Trimming. In this example, StitchingParams defines an eyelet staple on the saddle of the magazine. TrimmingParams defines the final size of the magazine. The rest of the collecting example is quite similar to the folding example.
