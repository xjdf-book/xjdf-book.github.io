Whereas a product description is process-independent and agnostic to the equipment of a particular print shop, a **process description** specifies the concrete manufacturing worksteps required to produce the product. Consequently, process descriptions are tailored to the specific machinery and production plan of the executing printing house.

The core of the XJDF Specification is Chapter 5 (“Processes”). **In XJDF, a *process* is synonymous with a workflow step: “Processes [...] define individual workflow steps that are assumed to be executed by a single-purpose Device.** Some controllers and devices are able to combine the functionality of multiple single-purpose devices and execute more than one process type” [@xjdf_ip1, chap. 5.1 "Combining Individual Process Steps"]—for example, a folding machine that can also slit, crease, or perforate sheets inline.

The XJDF Specification defines a comprehensive catalog of processes covering prepress, press, and postpress operations. As technology in the graphic arts industry evolves, CIP4 working groups continuously refine and expand this catalog. For specialized equipment that is not covered by standard processes, “vendors that have specific Processes that do not fit in the general XJDF processes and that are not combinations of individual XJDF processes can create XJDF Process Nodes of their own type” [@xjdf_ip1, chap. 3.5.5 "Extending Process Types"] (see “Extensibility” in Chapter 3).

In the specification, every process is defined by:

1. Its unique **process name** (used in `/XJDF/@Types`)
2. A **semantic description** of the manufacturing step
3. Two normative tables listing its **Input Resources** and **Output Resources**

In addition to process-specific resources, the specification defines a set of **Generic Input Resources** that are valid for any process—such as `NodeInfo` (“contains information about planned scheduling” [@xjdf_ip1, chap. 6.60 "NodeInfo"]) and `Device` (“describes the physical properties of the main device that executes an XJDF process” [@xjdf_ip1, chap. 6.28 "Device"]). The complete table of Generic Input Resources is defined in Section 5.2 (“Process Template”) of the XJDF Specification.

Following the process title and overview, the **Input Resources** and **Output Resources** tables specify which resources the `Folding` process consumes and produces. Here, `Folding` takes two optional input resources (`Component` and `FoldingParams`, plus any Generic Input Resources) and produces one optional output resource (`Component`). The question mark (`?`) following each resource name indicates that the resource is optional (`0..1` cardinality); full cardinality notation rules are defined in Section 1.6.4 (“Specification of Cardinality”) of the XJDF Specification.

* **`Component`** “is used to describe the various versions of finished and semi-finished goods in the press and postpress area, such as a pile of folded sheets that have been collected and are then be joined and trimmed. Nearly every postpress process has a Component resource as an input as well as an output. Typically the first components in the process chain are some printed sheets or ribbons, while the last Component is a book or a brochure” [@xjdf_ip1, chap. 6.18 "Component"].
* **`FoldingParams`** “describes the folding parameters, including the sequence of folding steps. It is also possible to execute the predefined steps of the folding catalog” [@xjdf_ip1, chap. 6.37 "FoldingParams"].

Below is the corresponding XJDF Document for a `"Folding"` Gray Box (first introduced in Chapter 3):

```xml title="Example: XJDF Gray Box 'Folding'"
<XJDF JobID="JOB-42" Types="Folding"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <AuditPool>
        <AuditCreated>
            <Header AgentName="MIS" AgentVersion="1.0"
                Time="2016-05-30T21:49:47Z" />
        </AuditCreated>
    </AuditPool>
    <ProductList>
        <Product Amount="2500" DescriptiveName="My Folded Leaflet">
            <Intent Name="LayoutIntent">
                <LayoutIntent Dimensions="841.88 595.27"
                        Sides="TwoSidedHeadToHead" Pages="2"
                        FinishedDimensions="280.69 595.27 0.0"/>
            </Intent>
            <Intent Name="FoldingIntent">
                <FoldingIntent FoldCatalog="F6-2"/>
            </Intent>
            <Intent Name="ColorIntent">
                <ColorIntent>
                    <SurfaceColor
                            ColorsUsed="Cyan Magenta Yellow Black"
                            Surface="Front"/>
                    <SurfaceColor
                            ColorsUsed="Cyan Magenta Yellow Black"
                            Surface="Back"/>
                </ColorIntent>
            </Intent>
            <Intent Name="MediaIntent">
                <MediaIntent MediaQuality="135_MATT"/>
            </Intent>
        </Product>
    </ProductList>
    <ResourceSet Name="Component" Usage="Input">
        <Resource ExternalID="COMP_ID_UNFOLDED">
            <Component Dimensions="841.88 595.27 0.42"
                    MediaRef="MEDIA-ID" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="Component" Usage="Output">
        <Resource ExternalID="COMP_ID_FOLDED">
            <AmountPool>
                <PartAmount Amount="2580" />
            </AmountPool>
            <Component Dimensions="280.69 595.27 1.26"
                    MediaRef="MEDIA-ID" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="FoldingParams" Usage="Input">
        <Resource>
            <FoldingParams FoldCatalog="F6-2"/>
        </Resource>
    </ResourceSet>
    <ResourceSet Name="Media">
        <Resource ID="MEDIA-ID">
            <Media MediaType="Paper" Thickness="150" Weight="135"
                    ISOPaperSubstrate="PS3" />
        </Resource>
    </ResourceSet>
    <ResourceSet Name="NodeInfo" Usage="Input">
        <Resource>
            <NodeInfo Start="2016-08-30T15:00:00Z" />
        </Resource>
    </ResourceSet>
</XJDF>
```

Notice how the `ResourceSet` elements in the document map directly to the specification table:

* The input `Component` and `FoldingParams` resources carry `//ResourceSet/@Usage="Input"`, and the Generic Input Resource `NodeInfo` also carries `@Usage="Input"`.
* The output `Component` resource carries `//ResourceSet/@Usage="Output"`.
* The `Media` `ResourceSet` omits `@Usage` because `Media` is neither a direct input nor an output of `Folding`; instead, it is referenced by the two `Component` resources (`//Component/@MediaRef="MEDIA-ID"`) to supply physical paper attributes such as `@Weight` and `@Thickness` needed for folder setup.

Because every process in the XJDF Specification has clearly defined input and output resources, complete production workflows can be chained together inside the MIS by linking the output interchange resource of one process to the input of the next. Importantly, this process chain exists inside the MIS—not inside a monolithic XML job ticket. For each job, the MIS plans the sequence of processes based on available equipment and device capabilities, groups those processes into **Gray Boxes** corresponding to the target devices or controllers, and generates a dedicated XJDF Document for each Gray Box.

Across this ten-process workflow, the seven Gray Boxes are connected by four primary **interchange resources**:

1. **`RunList`** — “defines one or more printable logical documents or document sets that MAY be defined in one or more external [...] files” [@xjdf_ip1, chap. 6.73 "RunList"] (digital PDF artwork and RIPped TIFF separations).
2. **`ExposedMedia`** — “represents a processed Media-based Resource such as film or plate” [@xjdf_ip1, chap. 6.35 "ExposedMedia"] (imaged printing plates from the plate setter).
3. **`Component`** — “is used to describe the various versions of semi-finished goods in the press and postpress area, such as a pile of folded sheets that have been collected and are then be joined and trimmed” [@xjdf_ip1, chap. 6.18 "Component"] (printed press sheets, cut piles, folded leaflets, and packaged boxes).
4. **`Product`** — The finished product delivered to the customer.

In addition to the interchange resource passed from the preceding step, each Gray Box receives process-specific parameter resources from the MIS. For example, **Gray Box 1 (`Preflight`)** receives the customer's artwork (`RunList`) along with preflight check rules (`PreflightParams`). “Preflighting is the process of examining the components of a print job to ensure that the job will print successfully and with the expected results. Preflight checks can be performed on each document or finished page identified within the associated RunList resource. Preflighting a file is generally a two-step process. First, the documents are analyzed and compared to the set of tests. Then, a preflight report is built to list the encountered issues (according to the tests)” [@xjdf_ip1, chap. 5.4.14 "Preflight"].

When `Preflight` finishes, it returns the checked artwork (`RunList`) and a `PreflightReport` detailing file metadata and any errors or warnings (such as missing fonts, incorrect trim box dimensions, or low-resolution images). Based on the `PreflightReport`, the MIS (or a prepress operator) decides whether to release the job to **Gray Box 2** or request corrected artwork. Notice that **Gray Box 2** encapsulates four distinct prepress processes executed together by a single prepress workflow system. **In XJDF, executing multiple processes within a single Gray Box is called a Combined Process.**


## Combined Processes
While all processes in the XJDF Specification “are assumed to be executed by a single-purpose device. Some controllers and devices are able to combine the functionality of multiple single-purpose devices and execute more than one process type” [@xjdf_ip1, chap. 5.1 "Combining Individual Process Steps"].

A classic example of a **Combined Process** is a prepress workflow system (**Gray Box 2** in the workflow diagram above), which prepares preflighted customer artwork for plate exposure or digital printing. In our folded leaflet workflow, Gray Box 2 combines four logical XJDF processes—`Stripping`, `Imposition`, `Interpreting`, and `Rendering`:

* **`Stripping`** “specifies the process of translating a high level structured description of the imposition of one or multiple job parts [...] for the Imposition process” [@xjdf_ip1, chap. 5.4.22 "Stripping"].
* **`Imposition`** “is responsible for combining pages of input graphical content onto surfaces of the physical output media. Static or dynamic printer's marks can be added to the surface in order to facilitate various aspects of the production process. Among other things, these marks are used for press alignment, color calibration, job identification and as guides for cutting and folding. Note that the Imposition process specifies the task of combining pages and marks on sheets. The task of setting up the parameters needed for Imposition is defined by Stripping” [@xjdf_ip1, chap. 5.4.8 "Imposition"].
* **`Interpreting` and `Rendering`** typically occur together as a pair inside a Raster Image Processor (RIP), which “consume page descriptions and instructions for producing the graphical output. It parses the graphical contents in the page descriptions, renders the contents, and produces a rasterized image of the page” [@jdf_1_5, chap. 6.2.33 "RIPing"].

Addressing a combined-process Gray Box follows the exact same principles as addressing a single-process Gray Box: its input resources are a subset of the union of input resources across the constituent processes, and its output resources correspond to the final process in the chain. Crucially, intermediate resources that are generated by one internal step and immediately consumed by the next do not need to be exposed in the XJDF Document: “A ResourceSet that is produced by one process and immediately consumed by the following process NEED NOT be explicitly specified in the XJDF. Any such ResourceSet MAY be completely under the control of the receiving device” [@xjdf_ip1, chap. 5.1.1 "Exchange ResourceSets in combined processes"].

In this prepress example, the XJDF Document supplies the inputs for `Stripping` and `Imposition` (a high-level `Layout` resource and the input artwork `RunList`) and declares the output of `Rendering` (an output `RunList` partitioned by `@Separation` pointing to the 1-bit TIFF files for `Cyan`, `Magenta`, `Yellow`, and `Black`). If the MIS needs finer control over internal steps within the Gray Box, it can simply include additional parameter resources—such as `RenderingParams` or `InterpretingParams`—as extra input `ResourceSet` elements.

Let us take a closer look at how the `Layout` resource is expressed for `Stripping` and `Imposition`. When the MIS wants to specify *how many* ups are placed on a press sheet (for cost estimation and paper planning) while leaving exact margin and mark calculations to the prepress imposition software, it uses **relative positioning** (`//Position/@RelativeBox`):

```xml title="Example: Layout definition with RelativeBox"
[...]
<ResourceSet Name="Layout" Usage="Input">
    <Resource>
        <Layout SurfaceContentsBox="0.0 0.0 1293.31 907.09"
                WorkStyle="WorkAndBack">
            <Position RelativeBox="0.0 0.0 0.5 1.0"
                    Orientation="Rotate90" BinderySignatureID="BS-1" />
            <Position RelativeBox="0.5 0.0 1.0 1.0"
                    Orientation="Rotate90" BinderySignatureID="BS-1" />
        </Layout>
    </Resource>
</ResourceSet>
[...]
```

Here, `//Layout/@SurfaceContentsBox` defines the press sheet dimensions (`1293.31 × 907.09` dtp points), and the two `Position` child elements place the folded leaflet (`@BinderySignatureID="BS-1"`) two-up on the sheet: one in the left half (`@RelativeBox="0.0 0.0 0.5 1.0"`) and one in the right half (`@RelativeBox="0.5 0.0 1.0 1.0"`), rotated by 90°. The `Stripping` process then computes the exact centered coordinates within each relative cell:

Unlike the prepress example (which omitted intermediate parameters), this Combined Process includes explicit parameter resources for all three steps in `/XJDF/@Types`:

* `Assembly` and `BinderySignature` configure the **`Collecting`** step (“Assembly describes how the sections of one or multiple Jobs or Job Parts are bound together” [@xjdf_ip1, chap. 6.4 "Assembly"]).
* `StitchingParams` configures the **`Stitching`** step (“provides the parameters for the Stitching process” [@xjdf_ip1, chap. 6.85 "StitchingParams"]).
* `TrimmingParams` configures the **`Trimming`** step (“provides the parameters for the Trimming process” [@xjdf_ip1, chap. 6.92 "TrimmingParams"]).

Meanwhile, the intermediate `Component` states (collected-but-unstitched signatures and stitched-but-untrimmed brochures) remain entirely internal to the saddle stitcher and are omitted from the XJDF Document; only the three initial pre-folded input components and the final trimmed output magazine (`COMP-MAGAZINE`) are specified.


## ProcessUsage
In most processes, every `ResourceSet` can be uniquely identified by the combination of its resource name (`//ResourceSet/@Name`) and its input/output direction (`//ResourceSet/@Usage`). Consider the input and output resource tables for the `Preflight` process from the XJDF Specification:

Even though `RunList` appears in both tables, the two `ResourceSet` elements are easily distinguished by their `@Usage` attribute (`"Input"` vs. `"Output"`):

```xml title="Example: RunList Resource as Input and Output"
[...]
<ResourceSet Name="RunList" Usage="Input" >
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/input.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
<ResourceSet Name="RunList" Usage="Output" >
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/output.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
[...]
```

Some processes, however, consume (or produce) **two distinct `ResourceSet` elements of the same type and with the same `@Usage`**. A prime example is the `Imposition` process, whose input resource table is shown below:

<figure>
  <Image src={screenImpositionInput} alt="Input Resources of an Imposition Process" />
  <figcaption>Figure: Input Resources of an Imposition Process</figcaption>
</figure>

Here, `Imposition` defines two separate input `RunList` resources:

1. `RunList (Document)` — a “structured list of incoming page contents which is transformed to produce the imposed surface images” [@xjdf_ip1, chap. 5 Table 5.26: Imposition/RunList(Document)].
2. `RunList (Marks)` — a “structured list of incoming marks. These are typically printer’s marks such as fold marks, cut marks, punch marks or color bars” [@xjdf_ip1, chap. 5 Table 5.26: Imposition/RunList(Marks)].

Because both resources reference external PDF files, both are modeled as input `RunList` `ResourceSet` elements. To distinguish between them, XJDF provides the `//ResourceSet/@ProcessUsage` attribute, whose value corresponds to the qualifier shown in parentheses next to the resource name in the specification table (`"Document"` vs. `"Marks"`):

```xml title="Example: RunList with ProcessUsage Definition"
[...]
<ResourceSet Name="RunList" Usage="Input" ProcessUsage="Document">
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/document.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
<ResourceSet Name="RunList" Usage="Input" ProcessUsage="Marks">
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/marks.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
<ResourceSet Name="RunList" Usage="Output">
    <Resource>
        <RunList>
            <FileSpec URL="http://example.org/output.pdf"/>
        </RunList>
    </Resource>
</ResourceSet>
[...]
```

Whenever two `ResourceSet` elements with the same `@Name` and `@Usage` coexist in an XJDF Document to represent different functional roles for a process, `//ResourceSet/@ProcessUsage` must be specified: “`@ProcessUsage` identifies the context of a Resource if multiple Resource elements of the same type are supplied for an individual process type” [@xjdf_ip1, chap. 3 Table 3.4: ResourceSet/@ProcessUsage].


## CombinedProcessIndex
In a Combined Process Gray Box, the same process type can even appear **more than once** in `/XJDF/@Types`—for example, `"Cutting Folding Cutting"`, where a sheet is cut before folding and trimmed/cut again immediately after folding within a single automated finishing line:

```xml title="Example: Gray Box 'Cutting Folding Cutting'"
<XJDF JobID="JOB-1234" Types="Cutting Folding Cutting"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

When a process type appears multiple times in `@Types` (or when two different processes in a Combined Process require separate input `ResourceSet` elements of the same type), the combination of `@Name`, `@Usage`, and `@ProcessUsage` is no longer sufficient to tell the device which `ResourceSet` belongs to which step in `@Types`. To resolve this ambiguity, XJDF provides the `//ResourceSet/@CombinedProcessIndex` attribute:

```xml title="Example: Gray Box 'Cutting Folding Cutting'"
<XJDF JobID="JOB-1234" Types="Cutting Folding Cutting"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
    <ResourceSet Name="CuttingParams" Usage="Input"
            CombinedProcessIndex="0">
        <Resource>
            <CuttingParams>
                [...]
            </CuttingParams>
        </Resource>
    </ResourceSet>
    <ResourceSet Name="CuttingParams" Usage="Input"
            CombinedProcessIndex="2">
        <Resource>
            <CuttingParams>
                [...]
            </CuttingParams>
        </Resource>
    </ResourceSet>
    <ResourceSet Name="FoldingParams" Usage="Input">
        <Resource>
            <FoldingParams FoldCatalog="F16-7"/>
        </Resource>
    </ResourceSet>
    [...]
</XJDF>
```

The attribute “`@CombinedProcessIndex` specifies the zero based indices of individual processes within the complete list of `XJDF/@Types` which this ResourceSet SHALL apply to. Multiple entries in `@CombinedProcessIndex` specify that the ResourceSet is used by the respective multiple processes. `@CombinedProcessIndex` SHALL be specified if multiple ResourceSet items with the same `@Name`, `@ProcessUsage`, and `@Usage` are specified in one XJDF. If `@CombinedProcessIndex` is not specified, the ResourceSet applies to all processes that match the `@Name`, `@ProcessUsage` and `@Usage` requirements” [@xjdf_ip1, chap. 3 Table 3.4: ResourceSet/@CombinedProcessIndex].

In XJDF, all indices are zero-based: “Thus, the first index is 0, the second index is 1, etc. Note that this restriction applies to the XJDF representation only. Display of values, for instance in a user interface, is implementation defined” [@xjdf_ip1, chap. 1.9.2 "Counting in XJDF"]. In `"Cutting Folding Cutting"`, the first `Cutting` step has index `0`, `Folding` has index `1`, and the second `Cutting` step has index `2`. Because `FoldingParams` appears only once and unambiguously matches `Folding`, it does not need a `@CombinedProcessIndex` attribute.


## Amounts
In production workflows, the `AmountPool` element “is a container for the amount-related metadata of the Resource [...]. The interpretation of the amounts specified in an AmountPool depends on the context of the AmountPool” [@xjdf_ip1, chap. 6.1.1 "AmountPool"]:

* When placed inside `/XJDF/ResourceSet/Resource`, `AmountPool` specifies **planned** quantities (the amount of input material allocated or the target amount of output to be produced).
* When placed inside `/XJDF/AuditPool/AuditResource` or inside an XJMF `SignalResource` message, `AmountPool` specifies **actual** quantities (the real amount of material consumed or produced).

The following excerpt from the collecting example shows a **planned** output quantity of 1,050 magazines specified inside the output `Component` resource:

```xml title="Example: Planned Amount Extract of the Collecting Example"
<XJDF JobID="JOB-1234" Types="Collecting Stitching Trimming"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
    <ResourceSet Name="Component" Usage="Output">
        <Resource ExternalID="COMP-MAGAZINE">
            <AmountPool>
                <PartAmount Amount="1050" />
            </AmountPool>
            <Component Dimensions="841.88 595.27 5.26" />
        </Resource>
    </ResourceSet>
    [...]
</XJDF>
```

`AmountPool` is an optional child element of `Resource` (placed first before `Part` and the specific resource element). Inside `AmountPool`, the `PartAmount` element's `@Amount` attribute specifies the good quantity “excluding waste, in units defined in `ResourceSet/@Unit` or implied by” [@xjdf_ip1, chap. 6 Table 6.3: PartAmount/@Amount] the resource's default unit. (**Note:** Units other than the default units defined in the XJDF Specification should not be used.) `PartAmount` also supports additional attributes such as `@Waste` to specify planned spoilage/waste allowances.

While planned amounts express what a Gray Box is instructed to consume or produce, **actual amounts** record what was physically consumed or produced on the shop floor. Actual amounts can be reported in two ways—both of which use a `ResourceInfo` container element:

1. **Post-facto inside the `AuditPool`** of the XJDF Document returned to the MIS upon job completion:

```xml title="Example: Actual Amount within an AuditPool element"
<XJDF JobID="JOB-1234" Types="Collecting Stitching Trimming"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
  [...]
  <AuditPool>
      <AuditResource>
          <Header ID="I43" DeviceID="DEV_ID"
                  Time="2017-01-11T13:58:19Z" />
          <ResourceInfo>
              <ResourceSet Name="Component" Usage="Output">
                  <Resource ExternalID="COMP-MAGAZINE">
                      <AmountPool>
                          <PartAmount Amount="1053" Waste="89" />
                      </AmountPool>
                      <Component Dimensions="841.88 595.27 5.26" />
                  </Resource>
              </ResourceSet>
          </ResourceInfo>
      </AuditResource>
  </AuditPool>
  [...]
</XJDF>
```

Inside `AuditPool`, each `AuditResource` element contains a standard `Header` followed by a `ResourceInfo` element wrapping a copy of the relevant `ResourceSet`. Comparing this `AuditResource` entry with the planned `ResourceSet` above shows the exact same XML structure—except that `PartAmount` now reports the actual post-facto production count of `@Amount="1053"` good magazines and `@Waste="89"` wasted copies. To log actual amounts for multiple resources (for example, both input consumption and output production), a separate `AuditResource` element is written for each `ResourceSet`.

2. **In real time during production via XJMF `SignalResource` messages** (covered in detail in Chapter 6):

```xml title="Example: Actual Amount within an XJMF Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="I2" DeviceID="DEV_ID"
            Time="2017-01-11T21:15:32+02:00" />
    <SignalResource>
        <Header ID="I43" DeviceID="DEV_ID"
                Time="2017-01-11T21:15:32+02:00" />
        <ResourceInfo JobID="JOB-1234" Speed="6000">
            <ResourceSet Name="Component" Usage="Output">
                <Resource ExternalID="COMP-MAGAZINE">
                    <AmountPool>
                        <PartAmount Amount="243" Waste="75" />
                    </AmountPool>
                    <Component Dimensions="841.88 595.27 5.26" />
                </Resource>
            </ResourceSet>
        </ResourceInfo>
    </SignalResource>
</XJMF>
```

`SignalResource` is the real-time XJMF counterpart to `AuditResource` in the `AuditPool`. Because an XJMF message has no `/XJDF/@JobID` root attribute, the job context (`@JobID="JOB-1234"`) and live machine telemetry (such as `@Speed="6000"`) are carried directly on the `ResourceInfo` element, while `PartAmount` reports the running counts produced so far (`@Amount="243"` good copies and `@Waste="75"` wasted copies).
