XJMF Bootstrapping describes the process of service discovery when connecting a controller or device. “XJMF currently provides no mechanism for initial device discovery. Thus, the URL of an XJMF device needs to be provided to a controller outside of XJMF. Once the XJMF URL is known, a controller SHOULD follow the steps below:” [@xjdf_ip1, chap. 9.6.7 "XJMF Bootstrapping"]

This illustration shows an MIS, a controller, and two devices. The focus in this illustration lies on the communication between the MIS and the controller. Each box visualize a synchronous communication between both. In all three boxes, the MIS sends a Query Message to the controller and receives a synchronous Response message in return. The combination of the three boxes is also known as XJMF Bootstrapping. The XJMF Bootstrapping consists of the steps “Messages Discovery”, “Devices Discovery”, and “Subscriptions Discovery”.

Bootstrapping is not limited to the MIS-to-Controller communication but it is also valid for the Controller-to-Device or MIS-to-Device communication.

## Step 1: Message Discovery

In the first step, the initiating system sends an XJMF KnownMessages Query Message to the system for it to detect. “The KnownMessages Query Message returns a list of all Message types that are supported by the controller” [@xjdf_ip1, chap. 7.7 "KnownMessages"] or device. The initiating system therefore gets an idea of which XJMF functionality is supported by the called system. Below is an example of such an XJMF KnownMessages Query Message:

```xml title="Example: XJMF KnownMessages Query Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T19:22:28+02:00" />
    <xjdf:QueryKnownMessages>
        <xjdf:Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T19:22:28+02:00" />
    </xjdf:QueryKnownMessages>
</xjdf:XJMF>
```

In most situations, an empty XJMF KnownMessages Query Message is enough to obtain a sufficient reply. The synchronous response of the Query Message is an XJMF KnownMessages Response Message:

```xml title="Example: XJMF KnownMessages Response Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-14T19:22:29+02:00" />
    <xjdf:ResponseKnownMessages ReturnCode="0">
        <xjdf:Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="CONTROLLER_ID"
                Time="2016-11-14T19:22:29+02:00" />
        <xjdf:MessageService Type="QueryKnownMessages"
                URLSchemes="http" />
        <xjdf:MessageService Type="QueryKnownDevices"
                URLSchemes="http" />
        <xjdf:MessageService Type="QueryKnownSubscriptions"
                URLSchemes="http" />
        <xjdf:MessageService Type="CommandSubmitQueueEntry"
                URLSchemes="http" />
        <xjdf:MessageService Type="CommandShutDown"
                URLSchemes="http" />
        <xjdf:MessageService Type="QueryStatus"
                URLSchemes="http" />
        [...]
    </xjdf:ResponseKnownMessages>
</xjdf:XJMF>
```

The XJMF KnownMessages Response message references the initiating Query message by its ID using the `@refID` attribute. Furthermore, the Response message contains “a list of MessageService elements. Each MessageService specifies one explicit message type that is supported by the device” [@xjdf_ip1, chap. 7.7.2.1 "MessageService"]. The message’s name can be found as the value of the attribute `@Type`. The meanings of the remaining attributes can be read in the XJDF Specification.

## Step 2: Devices Discovery

In the second step of the XJMF Bootstrapping process, the devices connected to the controller or the device itself are being discovered. An XJMF KnownDevices Query Message is therefore sent to the recipient. “The KnownDevices Query Message requests information about the Devices that are controlled by a controller [...]. The response is a list of device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"]. Here is an example of such a Query Message:

```xml title="Example: XJMF KnownDevices Query Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:26:07+02:00" />
    <xjdf:QueryKnownDevices>
        <xjdf:Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T20:26:07+02:00" />
        <xjdf:DeviceFilter DeviceDetails="Brief"/>
    </xjdf:QueryKnownDevices>
</xjdf:XJMF>
```

The example has previously been shown in the chapter “Query Message”. The message contains a subelement DeviceFilter. “The DeviceFilter Element refines the list of Devices that are requested to be returned” [@xjdf_ip1, chap. 7.6.1.1 "DeviceFilter"]. The usage of the value “Brief” in the attribute `@DeviceDetails` stipulates that the response should only provide the attribute DeviceID for each device listed in the DeviceList element. The corresponding Response Message is as follows:

```xml title="Example: XJMF KnownDevices Response Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T11:51:14+02:00" />
    <xjdf:ResponseKnownDevices ReturnCode="0">
        <xjdf:Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T11:51:14+02:00" />
        <xjdf:Device DeviceID="DEVICE-I" />
        <xjdf:Device DeviceID="DEVICE-II" />
    </xjdf:ResponseKnownDevices>
</xjdf:XJMF>
```

The XJMF KnownDevices Response Messages lists all devices which are controlled by the controller. For the initial discovery, this information should be sufficient. Should more information be required, the attribute `@DeviceDetails` in the Query Message can be set to “Full” in order to obtain the maximum amount of available device information from the controller.

## Step 3: Subscriptions Discovery

The last step of the XJMF Bootstrapping process is the subscriptions discovery. “The KnownSubscriptions XJMF enables controllers to query devices for a list of active persistent channels” [@xjdf_ip1, chap. 7.8 "KnownSubscriptions"]. The following snippet shows the XJMF KnownSubscriptions Query Message:

```xml title="Example: XJMF KnownSubscriptions Query Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    <xjdf:QueryKnownSubscriptions>
        <xjdf:Header ID="MESSAGE_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    </xjdf:QueryKnownSubscriptions>
</xjdf:XJMF>
```

The message is straightforward, as it does not require any subelements. An optional subelement is the SubscriptionFilter element. “The SubscriptionFilter element is a filter to limit the list of SubscriptionInfo elements that are returned in the KnownSubscriptions Response” [@xjdf_ip1, chap. 7.8.1.1 "SubscriptionFilter"]. All attributes which are marked as filterable in the table “Attributes of a persistent channel” in chapter “Persistent Channel” can be selected to filter the result.

The response to an XJMF KnownSubscriptions Query Message is an XJMF KnownSubscriptions Response Message, and it contains all details requested. Below is an example of such a Response Message:

```xml title="Example: XJMF KnownSubscriptions Response Message"
<xjdf:XJMF xmlns:xjdf="http://www.CIP4.org/JDFSchema_2_0">
    <xjdf:Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T21:07:14+02:00" />
    <xjdf:ResponseKnownSubscriptions ReturnCode="0">
        <xjdf:Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T21:07:14+02:00" />
        <xjdf:SubscriptionInfo ChannelID="CNL_1" DeviceID="MIS_ID"
                MessageType="Status">
            <xjdf:Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </xjdf:SubscriptionInfo>
        <xjdf:SubscriptionInfo ChannelID="CNL_2" DeviceID="MIS_ID"
                MessageType="Notification">
            <xjdf:Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </xjdf:SubscriptionInfo>
        <xjdf:SubscriptionInfo ChannelID="CNL_2" DeviceID="MIS_ID"
                MessageType="Resource">
            <xjdf:Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </xjdf:SubscriptionInfo>
    </xjdf:ResponseKnownSubscriptions>
</xjdf:XJMF>
```

The body of the XJMF KnownSubscriptions Response Message is a list of SubscriptionInfo elements. Each Subscription element describes an individual persistent channel.

“A Controller SHOULD NOT send a new subscription if a matching subscription is already in place in the device. If the device does not support QueryKnownSubscriptions, the controller MAY create a new subscription. A device that receives a subscription of the same type to the same URL SHOULD replace the existing subscription with the new subscription.

A controller SHOULD remove persistent channels that are no longer evaluated by sending a CommandStopPersistentChannel to a device” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].
