Besides the synchronous method of querying information from a controller or a device, XJMF provides another mechanism to do this asynchronously. Instead of getting a synchronous Response Messages to a Query, a subscription initiates asynchronous Signal Messages from a controller or device periodically, and whenever a change of state occurs. For instance, an XJMF Status Signal Message can be emitted from a device every 30 seconds, and whenever its state changes. The periodical signal is similar to a heartbeat of the device (if a device could have a heartbeat), and each change of state immediately causes an additional signal. The tracking system therefore receives a periodical update on the counters, the amount of resource consumption, etc., but can also promptly track all (critical) changes of state related to the device. In order to set up a Subscription, the MIS has to send an XJMF Subscription Message to the controller (or device). The system on the receiving end creates a new persistent channel specific to the message, which then sends the requested Signal Messages to the target URL configured in the Subscription Message. The persistent channel can be removed by sending a StopPersistentChannel Command Message to the producer.

Subscriptions and their corresponding persistent channels are typically used by MIS’s in order to track the activity of connected controllers and devices. In general, Subscriptions can be used for any kind of production tracking purposes.

The most common three subscription types are Status, Notification, and Resource. A Status Signal Message contains “the general status of a device or a controller and the status of jobs associated with this device or controller. No job context is needed to issue a Status message” [@xjdf_ip1, chap. 7.18 "Status"]. The Notification Signal Message contains notifications produced by the controller or device. “Notification elements are also used to signal usual events due to any activities of a device, operator, etc. (e.g., scanning a barcode)” [@xjdf_ip1, chap. 7.10 "Notification"]. The Resource Signal Message contains information related to the Resources, such as consumption, and so on.

In order to turn a Query Message into a subscription, an additional Subscription element has to be written into the message’s body. The following is an example of an XJMF Status Subscription Message:

```xml title="Example: XJMF Status Subscription Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T13:22:01+02:00" />
    <QueryStatus>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T13:22:01+02:00" />
        <Subscription RepeatTime="30"
                URL="http://mis.example.org/xjmf" />
        <StatusQuParams />
    </QueryStatus>
</XJMF>
```

“Queries SHALL be subscribed by including a Subscription element that defines the details of the subscription. The receiver of the subscription SHALL initially send an empty Response Message to the sender. The receiver of the subscription SHALL send XJMF Signals whenever the conditions that were specified in the Subscription element are met. Such a subscribed query that requests multiple Signals is referred to as a ‘persistent channel’.

[...] If a Controller that does not support persistent channels is queried to set up a persistent channel, it SHALL answer the Query Message with a Response Message and set the `@ReturnCode` to ‘111’” [@xjdf_ip1, chap. 9.6.2 "Subscribing for Signals"].

The conditions in the above example stipulate sending a Signal Message at least every 30 seconds, as specified in the attribute `@RepeatTime`. The attribute `@URL` defines the target URL to which the Signal Message is to be sent.

## Persistent Channel

A persistent channel is responsible for sending asynchronous Signal Messages (periodically) to a subscriber. Each channel is defined by its ChannelID, the subscribing message type, the DeviceID, and the URL of the receiving system. Furthermore, each channel has additional attributes such as `@RepeatTime`, `@RetryPolicy`, and `@ChannelMode` in order to configure their behavior. The following table shows all relevant attributes relating to persistent channels:

| Attribute | Filter | Description |
| --- | --- | --- |
| `ChannelID` (required) | yes | The unique identifier of the persistent channel. “ChannelID specifies the ID of the Query message that initiated the Subscription. `@ChannelID` SHALL match `Header/@refID` of all Signals that comprise this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@ChannelID]. |
| `DeviceID` (required) | yes | “`@DeviceID` of the controller that subscribed for the persistent channel. `@DeviceID` SHALL match `@DeviceID` of the query that subscribed for this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@DeviceID]. |
| `MessageType` (required) | yes | The message type of the Query Message being subscribed. For instance, in case a QueryStatus has created this channel, this Property has the value “Status”. |
| `URL` (required) | yes | “URL of the persistent channel receiving end” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@URL]. |
| `RepeatTime` | no | Update of the Signal Message “every `@RepeatTime` seconds. If defined, the Signal is generated periodically independent of any other trigger conditions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RepeatTime]. |
| `ChannelMode` | no | “Specifies reliability of persistent channel, and whether it is required or just preferred” [@xjdf_ip1, chap. 7.2.1.1 "Subscription/@ChannelMode"]. |
| `RetryPolicy` | no | “For reliable subscriptions. Indicates whether or not signals should be retried indefinitely, or only until the next Signal from the same Subscription (i.e., has the same `Header/@refID`) would be sent. `@RetryPolicy` is ignored for non-reliable subscriptions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RetryPolicy]. |

More details about the attributes and their effects on a production system can be read in the XJDF Specification. “Persistent channels SHOULD be maintained even when a device is powered off and powered on again” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].

While Query Messages containing a Subscription element set up a new persistent channel, the XJMF StopPersistentChannel Command Message removes a persistent channel. “No more Signal Messages are sent to the Controller once the command has been issued. A certain subset of signals MAY be addressed for unsubscription by specifying a StopPersChParams Element” [@xjdf_ip1, chap. 7.19 "StopPersistentChannel"]. The following is an example of such a Command Message:

```xml title="Example: XJMF StopPersistentChannel Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T15:26:59+02:00" />
    <CommandStopPersistentChannel>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T15:26:59+02:00" />
        <StopPersChParams URL="http://mis.example.org/xjmf" />
    </CommandStopPersistentChannel>
</XJMF>
```

The Command Message example above deletes all persistent channels created by the device “DEVICE_ID_MIS” and which are targeted towards the URL “*http://mis.example.org/jmf*”. All attributes marked as Filter = “yes” in the persistent channel Attribute Table can be used in the StopPersChParams element as a means of defining a subset of persistent channels to be removed. Attributes that are not specified default to match anything.
