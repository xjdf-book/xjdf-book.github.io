The three primary actors in an XJDF workflow are the **Management Information System (MIS)**, **Controllers**, and **Devices**:

* **MIS:** “The highest level Controller in a workflow is known as Management Information Systems or MIS. It is responsible for dictating and monitoring the execution of all of the diverse aspects of the workflow. This task is facilitated by access to production information, either in real time using XJMF messaging or post facto using the audit records within a returned XJDF” [@xjdf_ip1, chap. 2.1.4.5 "Management Information System - MIS"].
* **Controller:** “Controllers route XJDF information to the appropriate devices. The minimum requirement of a Controller is that it can initiate processes on at least one Device [...]. Controllers can also determine process planning and scheduling data, such as process times and planned production amounts” [@xjdf_ip1, chap. 2.1.4.4 "Controller"].
* **Device:** “The most basic function of a Device is to execute the information specified and routed by a Controller. Devices SHALL be able to execute the instructions that are specified in XJDF and [...] can perform the physical execution” [@xjdf_ip1, chap. 2.1.4.2 "Device"].

In most conventional print-shop architectures, production devices are not connected directly to the MIS. Instead, a vendor-specific **Controller** sits between the MIS and the shop-floor devices of that vendor, acting as an integration gateway:

</figure>

In this proxy architecture, the Controller encapsulates the underlying Devices: communication between the MIS and the Controller uses standard XJDF/XJMF, whereas communication between the Controller and its connected presses or finishers typically relies on a proprietary vendor protocol. For example, integrating a Heidelberg press requires “Heidelberg Prinect” as a Controller, just as a Koenig & Bauer (KBA) press requires “KBA LogoTronic.” While vendor controllers often provide helpful local scheduling and pressroom management features for shops without a full-featured MIS, they also introduce a single point of failure: if the central controller goes down, all devices behind it become unreachable.

In highly automated production environments—where the MIS handles all scheduling and orchestration centrally—a cleaner, more resilient architecture connects each device directly to the MIS via native XJDF/XJMF without an intermediate controller proxy:

**XJMF (Exchange Job Messaging Format)** is the real-time messaging protocol that accompanies XJDF, providing the communication infrastructure between the MIS, Controllers, and Devices. “A workflow is a dynamic set of interacting controllers and devices. For the workflow to run efficiently, these controllers and devices need to communicate and interact in a well defined manner. Whereas XJDF will typically be submitted to a device and only be returned after the process has been executed, XJMF messages MAY be exchanged at any time. Typical use cases for XJMF include but are not limited to:

* System setup
* Dynamic status and error tracking for Jobs and Devices
* Pipe control
* Device setup and Job changes
* Queue handling and Job submission
* Device Capability description” [@xjdf_ip1, chap. 7 "XJMF Messaging Format"]

“XJMF and XJDF have inherently different structures. In order to allow immediate identification of messages, XJMF uses the unique name XJMF as its own root-element name. XJMF elements SHALL contain one or more messages that provide more detailed information” [@xjdf_ip1, chap. 7.1 "XJMF Root"]. Unlike full job tickets, XJMF messages are compact, lightweight XML payloads—often just a few lines long. Below is a `QueryKnownDevices` message illustrating the standard XJMF structure:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-10T21:35:14+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-10T21:35:14+02:00" />
        <DeviceFilter DeviceDetails="Brief" />
    </QueryKnownDevices>
</XJMF>
```

“The KnownDevices Query Message requests information about the devices that are controlled by a controller. [...] The response is a list of device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"]. This message is typically sent by the MIS during initial discovery to find out which devices a controller manages.

Notice that an XJMF payload contains two `Header` elements:

1. **The outer `/XJMF/Header` element** identifies the system that transmitted the XJMF envelope (`@DeviceID`), the timestamp when the envelope was sent (`@Time`), and a unique identifier for the envelope (`@ID`).
2. **The inner message `Header` element** (e.g., `/XJMF/QueryKnownDevices/Header`) identifies the system that originally created the individual message (`@DeviceID`), when that message was generated (`@Time`), and the unique `@ID` of the message itself.

When the MIS sends a message directly, the `@DeviceID` and `@Time` values in both headers are identical. However, when a message originates on a shop-floor Device and is forwarded to the MIS by an intermediate proxy Controller, the two headers differ: `/XJMF/Header` records the `@DeviceID` and forwarding timestamp of the proxy Controller, whereas the inner message `Header` preserves the `@DeviceID` and original generation timestamp of the Device that triggered the event.

Furthermore, the inner message `Header/@ID` is used to correlate request and response messages (or subscriptions and asynchronous signals): every message triggered in reply to a previous message references the initiating message's `@ID` in its `Header/@refID` attribute.

Finally, each message type defines its own body elements—here, `DeviceFilter` with `@DeviceDetails="Brief"`, which instructs the controller to “provide only `Device/@DeviceID`” [@xjdf_ip1, chap. 7 Table 7.18: DeviceFilter/@DeviceDetails] in its response.


## Message Families
Every XJMF “Message belongs to one of four message families. These families are Query, Command, Signal and Response” [@xjdf_ip1, chap. 7.2 "XJMF Message Families"]. In XML, each message is represented by a child element of `XJMF` whose tag name combines the message family prefix (`Query`, `Response`, `Command`, or `Signal`) with the message type name—for example:

* `QueryKnownDevices`
* `ResponseKnownDevices`
* `CommandShutDown`
* `CommandSubmitQueueEntry`
* `SignalStatus`

The four message families categorize messages by their communication pattern and their effect on the receiver:

### Query Message
“A Query is a message that retrieves information from a receiver without changing the state of that receiver. [...] The receiver SHALL synchronously respond to a Query with an XJMF that contains abstract response of the same type as the” [@xjdf_ip1, chap. 7.2.1 "Query"] query. For instance, a `QueryKnownDevices` message must be answered synchronously with a `ResponseKnownDevices` message:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-10T21:35:14+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-10T21:35:14+02:00" />
        <DeviceFilter DeviceDetails="Brief" />
    </QueryKnownDevices>
</XJMF>
```

Because queries are side-effect-free read operations, they are used for service discovery and status polling without altering the state of the queried controller or device.

### Response Message
“A Response is a Message that a Receiver SHALL synchronously send to a sender as a response to a message” [@xjdf_ip1, chap. 7.2.4 "Response"]. Every `Query` or `Command` message is answered synchronously by a `Response` message of the matching type. Below is the controller's `ResponseKnownDevices` reply to the `QueryKnownDevices` message above:

```xml title="Example: XJMF KnownDevices Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJDF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-11T11:51:14+02:00" />
    <ResponseKnownDevices ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-11T11:51:14+02:00" />
        <Device DeviceID="PRESS-01" />
        <Device DeviceID="PRESS-02" />
        <Device DeviceID="PRESS-03" />
    </ResponseKnownDevices>
</XJMF>
```

In this response, `@DeviceID="DEVICE_ID_CONTROLLER"` identifies the responding controller, and `//Header/@refID="MESSAGE_ID"` points back to the `@ID` of the initiating `QueryKnownDevices` message.

Every `Response` element also carries an `@ReturnCode` attribute: “`@ReturnCode` summarizes the result of the Response. The value ‘0’ indicates success. `@ReturnCode` SHALL be provided if an error occurred” [@xjdf_ip1, chap. 7 Table 7.8: Response/@ReturnCode]. XJDF standardizes integer return codes across ranges: “Return code values are integers. Error messages below 100 are reserved for protocol errors. Error messages above 100 are used for device and controller errors and error messages above 200 for job and pipe specific errors” [@xjdf_ip1, Appendix B - Return Values and Error Codes].

Finally, the body of `ResponseKnownDevices` lists the three devices managed by the controller (`PRESS-01`, `PRESS-02`, and `PRESS-03`). Because the query requested `@DeviceDetails="Brief"`, each `Device` element includes only its `@DeviceID`; if `@DeviceDetails="Full"` had been requested, each `Device` element would include all available device metadata.

### Command Message
“A Command is syntactically equivalent to a Query, but rather than simply retrieving information, it also causes a state change in the receiver. A Command is used to change the state of the receiver. The receiver SHALL synchronously respond to a Command with an XJMF that contains a Response of the same type as the Command” [@xjdf_ip1, chap. 7.2.2 "Command"].

A simple example is `CommandShutDown`, which “shuts down a Controller or Device” [@xjdf_ip1, chap. 7.17 "ShutDown"] (or places it into standby mode, as specified by `ShutDownCmdParams/@ShutDownType="StandBy"`):

```xml title="Example: XJMF ShutDown Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-11T13:03:38+02:00" />
    <CommandShutDown>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-11T13:03:38+02:00" />
        <ShutDownCmdParams ShutDownType="StandBy"/>
    </CommandShutDown>
</XJMF>
```

In addition to controlling device state, `Command` messages are used to submit and manage XJDF jobs in a device queue—most notably via `CommandSubmitQueueEntry` (discussed in detail in “Submission of XJDF Documents” below):

```xml title="Example: XJMF SubmitQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandSubmitQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-12T12:11:39+02:00" />
        <QueueSubmissionParams
                URL="http://mis.example.org/job-1234.xjdf"
                ReturnJMF="http://mis.example.org/xjmf" Priority="42"/>
    </CommandSubmitQueueEntry>
</XJMF>
```

### Signal Message
“A Signal is a Message that a receiver of a Query with a subscription SHALL asynchronously send whenever the conditions specified in the Subscription are true. [...] Signals are typically sent from a device to a controller” [@xjdf_ip1, chap. 7.2.3 "Signal"] (or MIS).

The example below shows a `SignalStatus` message, which reports “the general status of a device or a controller and the status of jobs associated with this device or controller. No job context is needed to issue a Status message” [@xjdf_ip1, chap. 7.18 "Status"]:

```xml title="Example: XJMF Status Signal Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <SignalStatus>
        <Header ID="I1234" refID="MESSAGE_ID" DeviceID="DEVICE_ID"
                Time="2016-11-12T12:11:39+02:00" />
        <DeviceInfo Status="Production" Speed="6000"
                 ProductionCounter="5425">
            <JobPhase JobID="Job-42" JobPartID="Front"
                Status="InProgress" QueueEntryID="I434" Amount="1343"
                StartTime="2016-12-28T10:40:00Z" PercentCompleted="31.66"
                Waste="85"/>
        </DeviceInfo>
    </SignalStatus>
</XJMF>
```

Because a `Signal` is emitted asynchronously in response to a prior subscription, `//SignalStatus/Header/@refID="MESSAGE_ID"` references the `@ID` of the `QueryStatus` message that established the subscription. Notice also how the outer `/XJMF/Header/@DeviceID` identifies the forwarding proxy (`"DEVICE_ID_CONTROLLER"`), while the inner `//SignalStatus/Header/@DeviceID` identifies the physical press (`"DEVICE_ID"`). Inside `SignalStatus`, one or more `DeviceInfo` elements report live device telemetry (`@Status="Production"`, `@Speed="6000"`, `@ProductionCounter="5425"`) along with a `JobPhase` child element detailing progress on the currently running job (`@JobID="Job-42"`, `@PercentCompleted="31.66"`, `@Amount="1343"`, `@Waste="85"`).


## Subscriptions
Rather than repeatedly polling a controller or device with synchronous `Query` messages, an MIS can subscribe to asynchronous `Signal` messages using an **XJMF Subscription**. Once a subscription is active, the controller or device pushes `Signal` messages to the subscriber both periodically (like a heartbeat, e.g., every 30 seconds) and immediately whenever a relevant state change or event occurs:

<figure>
  <Image src={diagramXjmfStatusSubscription} alt="XJMF Status Subscription" />
  <figcaption>Figure: XJMF Status Subscription</figcaption>
</figure>

To establish a subscription, the MIS sends a `Query` message containing a `Subscription` child element specifying the target callback `@URL` and trigger parameters. The receiving controller or device replies synchronously with an initial `Response` message and opens a **persistent channel** that pushes asynchronous `Signal` messages to the callback `@URL` until the subscriber cancels the channel via a `CommandStopPersistentChannel` message.

The three most widely used subscriptions for production tracking are:

1. **`Status` (`QueryStatus` → `SignalStatus`):** Reports “the general status of a device or a controller and the status of jobs associated with this device or controller. No job context is needed to issue a Status message” [@xjdf_ip1, chap. 7.18 "Status"].
2. **`Notification` (`QueryNotification` → `SignalNotification`):** Reports operational events, warnings, and errors—“Notification elements are also used to signal usual events due to any activities of a device, operator, etc. (e.g., scanning a barcode)” [@xjdf_ip1, chap. 7.10 "Notification"].
3. **`Resource` (`QueryResource` → `SignalResource`):** Reports live material consumption and output production quantities (`AmountPool`).

Adding a `Subscription` element to any subscribable `Query` message turns it into a subscription request, as shown below for `QueryStatus`:

```xml title="Example: XJMF Status Subscription Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T13:22:01+02:00" />
    <QueryStatus>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T13:22:01+02:00" />
        <Subscription RepeatTime="30"
                URL="http://mis.example.org/xjmf" />
        <StatusQuParams />
    </QueryStatus>
</XJMF>
```

“Queries SHALL be subscribed by including a Subscription element that defines the details of the subscription. The receiver of the subscription SHALL initially send an empty Response Message to the sender. The receiver of the subscription SHALL send XJMF Signals whenever the conditions that were specified in the Subscription element are met. Such a subscribed query that requests multiple Signals is referred to as a ‘persistent channel’. [...] If a Controller that does not support persistent channels is queried to set up a persistent channel, it SHALL answer the Query Message with a Response Message and set the `@ReturnCode` to ‘111’” [@xjdf_ip1, chap. 9.6.2 "Subscribing for Signals"].

In the example above, `@RepeatTime="30"` instructs the device to emit a `SignalStatus` message at least every 30 seconds (in addition to immediate signals upon state changes) to `@URL="http://mis.example.org/xjmf"`.

### Persistent Channel
Every active subscription is managed as a **persistent channel** characterized by the attributes listed in the table below:

| Attribute | Filter | Description |
| --- | --- | --- |
| `ChannelID` (required) | yes | Unique identifier of the persistent channel: “ChannelID specifies the ID of the Query message that initiated the Subscription. `@ChannelID` SHALL match `Header/@refID` of all Signals that comprise this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@ChannelID]. |
| `DeviceID` (required) | yes | “`@DeviceID` of the controller that subscribed for the persistent channel. `@DeviceID` SHALL match `@DeviceID` of the query that subscribed for this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@DeviceID]. |
| `MessageType` (required) | yes | The message type of the subscribed query (e.g., `"Status"` for a channel created by `QueryStatus`). |
| `URL` (required) | yes | “URL of the persistent channel receiving end” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@URL]. |
| `RepeatTime` | no | Heartbeat interval: emits a `Signal` message “every `@RepeatTime` seconds. If defined, the Signal is generated periodically independent of any other trigger conditions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RepeatTime]. |
| `ChannelMode` | no | “Specifies reliability of persistent channel, and whether it is required or just preferred” [@xjdf_ip1, chap. 7.2.1.1 "Subscription/@ChannelMode"]. |
| `RetryPolicy` | no | “For reliable subscriptions. Indicates whether or not signals should be retried indefinitely, or only until the next Signal from the same Subscription (i.e., has the same `Header/@refID`) would be sent. `@RetryPolicy` is ignored for non-reliable subscriptions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RetryPolicy]. |

“Persistent channels SHOULD be maintained even when a device is powered off and powered on again” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].

To close one or more persistent channels, the subscriber sends a `CommandStopPersistentChannel` message: “No more Signal Messages are sent to the Controller once the command has been issued. A certain subset of signals MAY be addressed for unsubscription by specifying a StopPersChParams Element” [@xjdf_ip1, chap. 7.19 "StopPersistentChannel"]:

```xml title="Example: XJMF StopPersistentChannel Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T15:26:59+02:00" />
    <CommandStopPersistentChannel>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T15:26:59+02:00" />
        <StopPersChParams URL="http://mis.example.org/xjmf" />
    </CommandStopPersistentChannel>
</XJMF>
```

Any attribute marked with `Filter = yes` in the table above (`@ChannelID`, `@DeviceID`, `@MessageType`, `@URL`) can be used on `StopPersChParams` to select which channels to close; omitted filter attributes match all channels created by the requesting `@DeviceID`.


## Submission of XJDF Documents
To submit XJDF Documents to controllers and devices and manage their execution lifecycle, XJMF models every target device as having an **input queue**: “In XJMF, a controller or device is assumed to have one input queue that accepts submitted jobs” [@xjdf_ip1, chap. 4.7 "Queue Support"], where “A queue is a representation of a device that receives, manipulates and stores multiple queue entry items for execution” [@xjdf_ip1, chap. 1 Table 1.4: Glossary (Queue)]. From the perspective of XJMF, every submitted XJDF Document corresponds to a **queue entry** on the receiving device.

The XJDF Specification defines five primary command/response pairs for queue management:

| MessageType | Description |
| --- | --- |
| `CommandSubmitQueueEntry`<br/>`ResponseSubmitQueueEntry` | “A job is submitted to a queue in order to be executed” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandReturnQueueEntry`<br/>`ResponseReturnQueueEntry` | “Returns a job that had been submitted with a SubmitQueueEntry to the queue that represents the controller that originally submitted the job” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandResubmitQueueEntry`<br/>`ResponseResubmitQueueEntry` | “Replaces a queue entry without affecting the entry’s parameters. The command is used, for example, for late changes to a submitted XJDF” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandModifyQueueEntry`<br/>`ResponseModifyQueueEntry` | “Modifies the properties of one or more QueueEntry elements” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandRequestQueueEntry`<br/>`ResponseRequestQueueEntry` | “A new Job is requested by the Device. This message is used to signal that a device has processing resources available” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |

* “SubmitQueueEntry initially submits a QueueEntry to a device. Modifications to a QueueEntry can be applied by using the ResubmitQueueEntry or ModifyQueueEntry command” [@xjdf_ip1, chap. 7.20 "SubmitQueueEntry"].
* “The ReturnQueueEntry Message returns a job that had been submitted with a SubmitQueueEntry to the controller that originally submitted the job. Note that this command is sent from the device to a controller and not from controller to device as is the case with most other queue handling commands” [@xjdf_ip1, chap. 7.16 "ReturnQueueEntry"].
* “Queue entries are accessed using a `@QueueEntryID` attribute, which the queue’s controller or device generates when it receives the submitted job, and which is returned in the SubmitQueueEntry Response Message. `@QueueEntryID` SHALL uniquely identify an entry within the scope of one queue. An implementation is free to choose the algorithm that generates `@QueueEntryID` values” [@xjdf_ip1, chap. 9.1.1 "Queue Entry ID Generation"].

  <figcaption>Figure: XJMF QueueEntry Submission and Return</figcaption>
</figure>

The diagram above illustrates the standard submission and completion lifecycle of an XJDF job:

1. **Job Submission (`CommandSubmitQueueEntry`):** The MIS submits an XJDF job to the controller or device:

```xml title="Example: XJMF SubmitQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandSubmitQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-12T12:11:39+02:00" />
        <QueueSubmissionParams
                URL="http://mis.example.org/xjdf/job-1234.xjdf"
                ReturnJMF="http://mis.example.org/xjmf" Priority="42"/>
    </CommandSubmitQueueEntry>
</XJMF>
```

Inside `QueueSubmissionParams`, `@URL` points to the XJDF Document to be executed, `@ReturnJMF` specifies the MIS callback endpoint where the device should send `CommandReturnQueueEntry` once the job finishes, and `@Priority="42"` sets the queue priority (“number from 0 to 100, where ‘0’ = lowest priority and ‘100’ = maximum priority” [@xjdf_ip1, chap. 7 Table 7.81: QueueSubmissionParams/@Priority]).

2. **Synchronous Acceptance (`ResponseSubmitQueueEntry`):** The receiving controller or device creates a queue entry and returns its newly assigned `@QueueEntryID` (`"1"`) and initial `@Status` (`"Waiting"`):

```xml title="Example: XJMF SubmitQueueEntry Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <ResponseSubmitQueueEntry ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-12T12:11:39+02:00"/>
        <QueueEntry QueueEntryID="1" Priority="42"
                Status="Waiting" />
    </ResponseSubmitQueueEntry>
</XJMF>
```

3. **Job Completion & Return (`CommandReturnQueueEntry`):** Once the job has been executed on the device, the controller or device sends a `CommandReturnQueueEntry` message to the `@ReturnJMF` endpoint of the MIS, referencing `@QueueEntryID="1"` and the `@URL` of the completed XJDF Document (which now contains the populated `AuditPool`):

```xml title="Example: XJMF ReturnQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandReturnQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-12T12:11:39+02:00" />
        <ReturnQueueEntryParams QueueEntryID="1"
                URL="http://controller.example.org/xjdf/job-1234.xjdf" />
    </CommandReturnQueueEntry>
</XJMF>
```

4. **Return Confirmation (`ResponseReturnQueueEntry`):** The MIS acknowledges receipt of the returned job with a `ResponseReturnQueueEntry` message (`@ReturnCode="0"`):

```xml title="Example: XJMF ReturnQueueEntry Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-12T12:11:39+02:00" />
    <ResponseReturnQueueEntry ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_MIS"
                Time="2016-11-12T12:11:39+02:00" />
    </ResponseReturnQueueEntry>
</XJMF>
```


## Interchange Protocol
“XJDF and XJMF SHOULD be exchanged over a network by using http […] or https. Controllers and devices SHOULD implement an http server. […] Controllers and devices SHOULD provide insecure http without a TLS layer for better interoperability” [@xjdf_ip1, chap. 9.5 "XJDF and XJMF Interchange Protocol"]. “XJMF Messaging does not specify a standard port” [@xjdf_ip1, chap. 9.5.1 "HTTP Port"].

“A sender SHALL use an http POST request to transmit an XJMF that contains XJMF Queries, XJMF Commands and XJMF Signals to an HTTP server. The contents SHALL be placed in the body of the http request. […]. The receiver SHALL package response messages as raw XML. The body of an HTTP response to an XJMF that contains only XJMF Signals that are not defined as reliable (`@ChannelMode`!="Reliable") MAY be empty” [@xjdf_ip1, chap. 9.5.2 "HTTP Request Method"].

The table below summarizes the key HTTP transport parameters:

| Parameter | Value |
| --- | --- |
| Protocol | HTTP / HTTPS |
| Port | Any (configured per endpoint URL) |
| HTTP Request Method | `POST` |
| Payload Location | HTTP Request / Response Body |

### Packaging
Because an XJMF message may reference an XJDF Document, and that XJDF Document may in turn reference external digital assets (such as PDF artwork or ICC color profiles), submitting a job by URL alone can create a chain of dependent HTTP downloads across the network. In distributed or cross-network setups, such multi-hop download chains can be fragile or blocked by firewalls.

To make job transfers self-contained, XJDF supports bundling an XJMF message, its referenced XJDF Document, and any associated digital assets into a single **ZIP package**: “Zip is a de facto industry standard for packaging and compressing data. Directory structures can be encoded in a ZIP package” [@xjdf_ip1, chap. 9.7.2 "ZIP Packaging"] (see *https://www.pkware.com/support/zip-app-note/*).

To ensure a well-defined entry point when unpacking an XJMF ZIP archive, the specification mandates a root message file: “The root XJMF SHALL be named root.xjmf and SHALL reside in the root directory of the ZIP package” [@xjdf_ip1, chap. 9.7.2.1 "Identifying the Root XJMF"]:

<figure>
  <Image src={screenZipRoot} alt="Root Directory ('/') of the ZIP Archive" />
  <figcaption>Figure: Root Directory (“/”) of the ZIP Archive</figcaption>
</figure>

When the recipient unpacks the archive, `root.xjmf` is parsed first. All files included inside the ZIP archive are referenced using relative local paths resolved from the root of the ZIP archive: “Referenced digital assets that reside in the ZIP package, [...] SHALL be referenced as local URLs. The current URL for calculating local URLs SHALL be the root of the ZIP package, regardless of the location of the referring digital asset within the ZIP package. Digital assets other than the root.xjmf MAY be placed in a directory tree structure within the ZIP file” [@xjdf_ip1, chap. 9.7.2.2 "Referencing Digital Assets within a ZIP Package"]. The figure below shows the contents of the `/assets/` subdirectory inside the archive:

<figure>
  <Image src={screenZipAssets} alt="Assets Subdirectory ('/assets/') of the ZIP Archive" />
  <figcaption>Figure: Assets Subdirectory (“/assets/”) of the ZIP Archive</figcaption>
</figure>

Accordingly, in `root.xjmf`, `QueueSubmissionParams/@URL` simply points to `"doc.xjdf"`, and inside `doc.xjdf`, the `FileSpec/@URL` attributes point to `"assets/asset_1.pdf"` and `"assets/asset_2.jpg"`.

“XJMF messages that do not refer to XJDF or external digital assets SHOULD NOT be packaged as zip. Digital assets that are not included in the zip package MAY be referenced. Multiple XJMF messages SHALL NOT be packaged in one zip package” [@xjdf_ip1, chap. 9.7 "XJDF Packaging"].

### Error Handling
“Error handling is an implementation-dependent feature of XJDF-based systems. The AuditPool element provides a container where errors that occur during the execution [...] SHOULD be logged using Notification elements. Notification elements MAY also be sent in XJMF messages” [@xjdf_ip1, chap. 9.3.8 "Error Handling"] in real time as soon as an error occurs.

Below is an example of an error logged inside `/XJDF/AuditPool/AuditNotification`:

```xml title="Example: AuditPool Error Notification"
[...]
<AuditPool>
    [...]
    <AuditNotification>
        <Header DeviceID="DEVICE_ID" ID="MESSAGE_ID"
            Time="2016-11-14T16:57:24+02:00" />
        <Notification Class="Error" JobID="JOB_ID">
            <Event EventID="3092" EventValue="Paper stock is low." />
        </Notification>
    </AuditNotification>
    [...]
</AuditPool>
[...]
```

Inside `AuditNotification`, the `Notification` element “contains information about individual events that occurred during processing” [@xjdf_ip1, chap. 7.10.3.1 "Notification"], classified by `@Class="Error"` (indicating an issue that requires operator intervention, such as depleted paper or toner) and linked to the affected job via `@JobID="JOB_ID"`.

To report the exact same error immediately in real time, the `Notification` element is sent inside an XJMF `SignalNotification` message:

```xml title="Example: XJMF Error Notification"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-14T16:57:24+02:00" />
    <SignalNotification>
        <Header ID="I1234" refID="MESSAGE_ID"
            DeviceID="DEVICE_ID" Time="2016-11-14T16:57:24+02:00" />
        <Notification Class="Error" JobID="JOB_ID">
            <Event EventID="3092" EventValue="Paper stock is low." />
        </Notification>
    </SignalNotification>
</XJMF>
```


## XJMF Bootstrapping
**XJMF Bootstrapping** is the three-step service discovery handshake performed when connecting an MIS (or controller) to a subordinate controller or device: “XJMF currently provides no mechanism for initial device discovery. Thus, the URL of an XJMF device needs to be provided to a controller outside of XJMF. Once the XJMF URL is known, a controller SHOULD follow the steps below:” [@xjdf_ip1, chap. 9.6.7 "XJMF Bootstrapping"]

<figure>
  <Image src={diagramXjmfBootstrapping} alt="XJMF Bootstrapping" />
  <figcaption>Figure: XJMF Bootstrapping</figcaption>
</figure>

As shown in the diagram, bootstrapping consists of three synchronous query/response pairs executed in sequence: **Step 1: Message Discovery**, **Step 2: Devices Discovery**, and **Step 3: Subscriptions Discovery**. (The exact same handshake applies whether an MIS is connecting to a Controller, a Controller to a Device, or an MIS directly to a Device.)

### Step 1: Message Discovery
First, the initiating system sends an empty `QueryKnownMessages` message to discover which XJMF messages the target endpoint supports: “The KnownMessages Query Message returns a list of all Message types that are supported by the controller” [@xjdf_ip1, chap. 7.7 "KnownMessages"] or device:

```xml title="Example: XJMF KnownMessages Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T19:22:28+02:00" />
    <QueryKnownMessages>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T19:22:28+02:00" />
    </QueryKnownMessages>
</XJMF>
```

The target endpoint replies synchronously with a `ResponseKnownMessages` message containing “a list of MessageService elements. Each MessageService specifies one explicit message type that is supported by the device” [@xjdf_ip1, chap. 7.7.2.1 "MessageService"]:

```xml title="Example: XJMF KnownMessages Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-14T19:22:29+02:00" />
    <ResponseKnownMessages ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="CONTROLLER_ID"
                Time="2016-11-14T19:22:29+02:00" />
        <MessageService Type="QueryKnownMessages"
                URLSchemes="http" />
        <MessageService Type="QueryKnownDevices"
                URLSchemes="http" />
        <MessageService Type="QueryKnownSubscriptions"
                URLSchemes="http" />
        <MessageService Type="CommandSubmitQueueEntry"
                URLSchemes="http" />
        <MessageService Type="CommandShutDown"
                URLSchemes="http" />
        <MessageService Type="QueryStatus"
                URLSchemes="http" />
        [...]
    </ResponseKnownMessages>
</XJMF>
```

### Step 2: Devices Discovery
Second, the initiating system sends a `QueryKnownDevices` message to discover the device(s) managed by the target endpoint: “The KnownDevices Query Message requests information about the Devices that are controlled by a controller [...]. The response is a list of device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"]:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:26:07+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T20:26:07+02:00" />
        <DeviceFilter DeviceDetails="Brief"/>
    </QueryKnownDevices>
</XJMF>
```

```xml title="Example: XJMF KnownDevices Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T11:51:14+02:00" />
    <ResponseKnownDevices ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T11:51:14+02:00" />
        <Device DeviceID="DEVICE-I" />
        <Device DeviceID="DEVICE-II" />
    </ResponseKnownDevices>
</XJMF>
```

Setting `DeviceFilter/@DeviceDetails="Brief"` returns the `@DeviceID` of each connected device (`"DEVICE-I"` and `"DEVICE-II"`); setting `@DeviceDetails="Full"` retrieves full device metadata.

### Step 3: Subscriptions Discovery
Third, the initiating system sends a `QueryKnownSubscriptions` message to check which persistent channels are already active on the controller or device: “The KnownSubscriptions XJMF enables controllers to query devices for a list of active persistent channels” [@xjdf_ip1, chap. 7.8 "KnownSubscriptions"]:

```xml title="Example: XJMF KnownSubscriptions Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    <QueryKnownSubscriptions>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    </QueryKnownSubscriptions>
</XJMF>
```

(If desired, a `SubscriptionFilter` child element can be included using any filterable attribute from the persistent channel table to narrow the query.) The target replies with a `ResponseKnownSubscriptions` message listing all active `SubscriptionInfo` entries:

```xml title="Example: XJMF KnownSubscriptions Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T21:07:14+02:00" />
    <ResponseKnownSubscriptions ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T21:07:14+02:00" />
        <SubscriptionInfo ChannelID="CNL_1" DeviceID="MIS_ID"
                MessageType="Status">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
        <SubscriptionInfo ChannelID="CNL_2" DeviceID="MIS_ID"
                MessageType="Notification">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
        <SubscriptionInfo ChannelID="CNL_3" DeviceID="MIS_ID"
                MessageType="Resource">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
    </ResponseKnownSubscriptions>
</XJMF>
```

Inspecting active subscriptions during bootstrapping prevents duplicate channels after restarts: “A Controller SHOULD NOT send a new subscription if a matching subscription is already in place in the device. If the device does not support QueryKnownSubscriptions, the controller MAY create a new subscription. A device that receives a subscription of the same type to the same URL SHOULD replace the existing subscription with the new subscription. A controller SHOULD remove persistent channels that are no longer evaluated by sending a CommandStopPersistentChannel to a device” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].


## Piping (Overlapping Processing)
Up to this point, we have looked at hierarchical communication between the MIS and individual controllers or devices, where one process step finishes before the next begins. However, XJMF also supports direct peer-to-peer coordination between devices for **overlapping processing (piping)**:

“Some processes, e.g. a long print run, take a long time to complete while constantly creating intermediate output that is already available for processing by a subsequent process prior to completion of the initial process. In overlapping processing, the controller sends an XJDF to the initial device and does not wait until the first XJDF has been processed before sending a subsequent XJDF that describes the next process step of the same job to a different device. The subsequent device MAY begin processing as soon as the initial device has produced sufficient resources for the subsequent device. The communication between the devices SHOULD use CommandPipeControl messages” [@xjdf_ip1, chap. 9.3.5 "Overlapping Processing"].

XJMF Piping is also used in physically coupled multi-vendor production lines—such as an automated Book-on-Demand line pairing a digital web press from Vendor A directly with an inline perfect binder/trimmer from Vendor B. Using `CommandPipeControl` messages, both devices coordinate directly in real time: if the finishing unit pauses, it signals the press to pause; if the finishing unit spoils a book block, it signals the press to reprint that specific book copy automatically. Full details on XJMF Piping can be found in Section 9.3.5 (“Overlapping Processing”) of the XJDF Specification.
