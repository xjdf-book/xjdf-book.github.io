The main actors involved in an XJDF Workflow are the Management Information System (MIS), Controllers, and Devices. “The highest level Controller in a workflow is known as Management Information Systems or MIS. It is responsible for dictating and monitoring the execution of all of the diverse aspects of the workflow. This task is facilitated by access to production information, either in real time using XJMF messaging or post facto using the audit records within a returned XJDF” [@xjdf_ip1, chap. 2.1.4.5 "Management Information System - MIS"].

“Controllers route XJDF information to the appropriate devices. The minimum requirement of a Controller is that it can initiate processes on at least one Device [...]. Controllers can also determine process planning and scheduling data, such as process times and planned production amounts” [@xjdf_ip1, chap. 2.1.4.4 "Controller"].

“The most basic function of a Device is to execute the information specified and routed by a Controller. Devices SHALL be able to execute the instructions that are specified in XJDF and [...] can perform the physical execution” [@xjdf_ip1, chap. 2.1.4.2 "Device"].

In a typical XJDF system architecture, the devices are not connected to the MIS directly. A Controller is usually involved in the communication. The Controller and the Devices normally stem from one and the same vendor, and the Controller is required in order to integrate the Devices into an XJDF Workflow System:

  <Image src={diagramArchWithController} alt="XJDF System Architecture WITH Controller" />

</figure>

As shown in the figure above, the Controller encapsulates the Device from the outside. In the real world, the communication between the devices and the controller is based on a non-standard data format, and the devices can only be addressed using the Controller as a proxy.

For instance, when using a Heidelberg Press (Device), the “Heidelberg Prinect” (Controller) is additionally required in order to interact with the press. The same goes for KBA. A KBA press requires “KBA Logotronic” (Controller) to be addressed from the outside using an official standard. In such an architecture, the controller is always the single point of failure. A breakdown of the controller causes a breakdown of all devices connected by the controller. In particular, this poses a real problem in highly automated systems. Unfortunately, this architecture is the dominating one.

A more flexible, robust, and more fail-safe architecture would be the ability to address the devices directly without any Controller at all:

  <Image src={diagramArchWithoutController} alt="XJDF System Architecture WITHOUT Controller" />

</figure>

Apart from the functionality of the proxy, many controllers provide additional functionality such as scheduling, etc. These features can be very useful, especially when no MIS exists or, the scheduling of the MIS is limited. However, the higher the level of automation in a printing house, the more important the stability and reliability of systems becomes. In highly automated systems, MIS systems are self-made, and controllers increasingly become more of an achilles heel for these systems.

XJMF is the messaging system that accompanies XJDF in order to provide a communication infrastructure between the MIS, the controllers, and the devices. “A workflow is a dynamic set of interacting controllers and devices. For the workflow to run efficiently, these controllers and devices need to communicate and interact in a well defined manner. Whereas XJDF will typically be submitted to a device and only be returned after the process has been executed, XJMF messages MAY be exchanged at any time. Typical use cases for XJMF include but are not limited to:

* System setup
* Dynamic status and error tracking for Jobs and Devices
* Pipe control
* Device setup and Job changes
* Queue handling and Job submission
* Device Capability description” [@xjdf_ip1, chap. 7 "XJMF Messaging Format"]

“XJMF and XJDF have inherently different structures. In order to allow immediate identification of messages, XJMF uses the unique name XJMF as its own root-element name. XJMF elements SHALL contain one or more messages that provide more detailed information” [@xjdf_ip1, chap. 7.1 "XJMF Root"]. XJMF Messages are essentially tiny XML structures. Many messages consist of only a few lines of code. In the following code snippet, an XJMF KnownDevices Query Message is shown to give an idea of the outline of the XML structure:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-10T21:35:14+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-10T21:35:14+02:00" />
        <DeviceFilter DeviceDetails="Brief" />
    </QueryKnownDevices>
</XJMF>
```

“The KnownDevices Query Message requests information about the devices that are controlled by a controller. [...] The response is a list of device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"] guided by the controller. Such a message is usually sent from the MIS to a controller during discovery.

The XJMF root element is a container for all kinds of messages. Each XJMF root element contains a Header element which specifies details about its sender. The attribute `@DeviceID` in the header contains the identifier of the sending device, and `@Time` contains the timestamp showing when the XJMF was generated. An unique identifier of the XJMF (`@ID`) is also required in the header.

In the example above, there is only one message in the XJMF - the KnownDevices Query Message. The message element also contains a Header element specifying the attributes `@DeviceID`, `@Time`, and `@ID`. In this situation, the values of the attributes `@DeviceID` and `@Time` are equal to the values contained in the XJMF’s Header element, since both the XJMF and the KnownDevices Query Message have been generated by one and the same system at the same time.

The attributes in the Header elements will differ as soon as a message is initiated by a device and proxied by a controller. In this situation, the XJMF the requesting system receives defines the controller’s DeviceID, as well as the timestamp of when the controller forwarded the messages in the XJMF Header element. The message’s header defines the DeviceID of the Device which originally initiated the message. The timestamp of the message also corresponds to the time it was initially generated. Even when the controller and the device communicate in a non-standard way, the message contains the header details of the initiating device.

In addition to the device’s identifier and the time, the message’s header also contains an `@ID` attribute. Each message has to contain an unique identifier in order to identify the message. This identifier is used for asynchronous feedback messages. All messages initiated by another message contain that message’s unique identifier in their `Header/@refID` attribute. This method allows for the allocation of messages.

The message's body is unique to each message. In the example above, it contains an element, DeviceFilter, and, additionally, a single attribute, `@DeviceDetails`. The attribute `@DeviceDetails` refines the level of provided information about the Devices listed in the Response message. The value “Brief” means “provide only `Device/@DeviceID`” [@xjdf_ip1, chap. 7 Table 7.18: DeviceFilter/@DeviceDetails].

The KnownDevices Query Message is a message of the family “Query”. Technically, each query requires one response. “Response” is another message family in XJMF.


## Message Families

Each XJMF “Message belongs to one of four message families. These families are Query, Command, Signal and Response” [@xjdf_ip1, chap. 7.2 "XJMF Message Families"]. Each message is expressed by an individual XML Element in the XJMF root element. The element's name is an aggregation of the message family and the message’s type. The corresponding message element of the query message “KnownDevices” is “QueryKnownDevices”. Further message elements are, for instance:

* QueryKnownDevices
* ResponseKnownDevices
* CommandShutDown
* CommandSubmitQueueEntry
* SignalStatus

Message families are some kind of categorization of the messages. In the following sections, all message families are introduced. Each message family bundles a set of similar messages which cause a similar behavior of the recipient.

### Query Message

“A Query is a message that retrieves information from a receiver without changing the state of that receiver. [...] The receiver SHALL synchronously respond to a Query with an XJMF that contains abstract response of the same type as the” [@xjdf_ip1, chap. 7.2.1 "Query"]. The KnownDevices Query Message, for instance, expects a KnownDevices Response Message as response. The following is an example of a “KnownDevices” query message:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-10T21:35:14+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-10T21:35:14+02:00" />
        <DeviceFilter DeviceDetails="Brief" />
    </QueryKnownDevices>
</XJMF>
```

This XJMF code snippet is the same as the one shown before. “The KnownDevices Query Message requests information about the devices that are controlled by a controller. [...] The response is a list of Device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"] controlled by the Controller that receives the query. A query does not influence the behavior of the receiver in any way according to the XJDF workflow. Queries are used during workflow discovery and for tracking purposes.

### Response Message

“A Response is a Message that a Receiver SHALL synchronously send to a sender as a response to a message” [@xjdf_ip1, chap. 7.2.4 "Response"]. Response messages are used for responding to a Query or Command message. Each Response message generated is of the same message type as the initiating message. Therefore, a KnownDevices Query Message has to be responded to by a KnownDevices Response Message. In the following example, a response message of type KnownDevices is presented as a result of the KnownDevices Query Message:

```xml title="Example: XJMF KnownDevices Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJDF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-11T11:51:14+02:00" />
    <ResponseKnownDevices ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-11T11:51:14+02:00" />
        <Device DeviceID="PRESS-01" />
        <Device DeviceID="PRESS-02" />
        <Device DeviceID="PRESS-03" />
    </ResponseKnownDevices>
</XJMF>
```

The `@DeviceID` value in the XJMF header, as well as in the response messages, corresponds to the identifier of the Controller (“DEVICE_ID_CONTROLLER”) since this message has been generated by the controller in response to the KnownDevices query. The response message contains the two additional attributes `//Header/@refID` and `@ReturnCode`.

The attribute `//Header/@refID` refers to the `@ID` Attribute of the initiating Message to which the Response refers. If not specified, the Response Message serves as a reference to the entire XJMF.

“`@ReturnCode` summarizes the result of the Response. The value ‘0’ indicates success. `@ReturnCode` SHALL be provided if an error occurred” [@xjdf_ip1, chap. 7 Table 7.8: Response/@ReturnCode]. XJDF comes with a set of predefined return codes. “Return code values are integers. Error messages below 100 are reserved for protocol errors. Error messages above 100 are used for device and controller errors and error messages above 200 for job and pipe specific errors” [@xjdf_ip1, Appendix B - Return Values and Error Codes]. The full list of all predefined error codes can be found in the XJDF Specification in Appendix B - “Return Values and Error Codes”

Because the KnownDevices Response message is a response to the KnownDevices Query message which queries a list of devices, the response message also contains the requested information. Therefore, the message provides the list of all devices controlled by the Controller. In the query message, there is an attribute `@DeviceDetails` which defines the value “Brief” - a value indicating “Provide only `Device/@DeviceID`” [@xjdf_ip1, chap. 7 Table 7.18: DeviceFilter/@DeviceDetails]. Thus, the device list in the message only lists the identifiers of the devices. When the attribute `@DeviceDetails` in the query is fed the value “Full”, the response message would have to list the maximum available device information for each device.

### Command Message

“A Command is syntactically equivalent to a Query, but rather than simply retrieving information, it also causes a state change in the receiver. A Command is used to change the state of the receiver. The receiver SHALL synchronously respond to a Command with an XJMF that contains a Response of the same type as the Command” [@xjdf_ip1, chap. 7.2.2 "Command"]. One example for a Command is the ShutDown Command Message. “The ShutDown Command Message shuts down a Controller or Device” [@xjdf_ip1, chap. 7.17 "ShutDown"].

```xml title="Example: XJMF ShutDown Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-11T13:03:38+02:00" />
    <CommandShutDown>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-11T13:03:38+02:00" />
        <ShutDownCmdParams ShutDownType="StandBy"/>
    </CommandShutDown>
</XJMF>
```

The ShutDown Command Message is a straightforward Command. There are no additional attributes - neither in the XJMF element, nor in the message element itself. The subelement ShutDownCmdParams specifies whether the receiver has to shut down completely, or just go into standby modus. More details on shutdown behavior can be found in the XJDF Specification. The expected response message from the Device or Controller is a ShutDown Response message containing a return code value of “0” (success).

Aside from the plain state changes of devices and controllers, command messages can also be used to transfer XJDF Documents from one point to the next in a XJDF Workflow. A SubmitQueueEntry Command Message, for instance, allows for the submission of an XJDF Document from the MIS to a controller or a device.

The submission of and interaction with XJDF Documents is described later in this chapter (“Submission of XJDF Documents”). Nevertheless, the following example shows a command message for the submission of an XJDF Document:

```xml title="Example: XJMF SubmitQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandSubmitQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-12T12:11:39+02:00" />
        <QueueSubmissionParams
                URL="http://mis.example.org/job-1234.xjdf"
                ReturnJMF="http://mis.example.org/xjmf" Priority="42"/>
    </CommandSubmitQueueEntry>
</XJMF>
```

The SubmitQueueEntry Command Message is a straightforward Command as well - it contains no additional attributes in the XJMF element or in the message element itself. The rest of the message will be explained later.

### Signal Message

“A Signal is a Message that a receiver of a Query with a subscription SHALL asynchronously send whenever the conditions specified in the Subscription are true. [...] Signals are typically sent from a device to a controller” [@xjdf_ip1, chap. 7.2.3 "Signal"] (or MIS). How to go about setting up and managing subscriptions is explained in detail in the next section on “Subscriptions”.

In the following, an XJMF example showing a Status Signal message is given. A Status Signal message contains details about “the general status of a device or a controller and the status of jobs associated with this device or controller. No job context is needed to issue a Status message” [@xjdf_ip1, chap. 7.18 "Status"]. The message contains one or more DeviceInfo elements, which in turn contain information specific to the device:

```xml title="Example: XJMF Status Signal Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <SignalStatus>
        <Header ID="I1234" refID="MESSAGE_ID" DeviceID="DEVICE_ID"
                Time="2016-11-12T12:11:39+02:00" />
        <DeviceInfo Status="Production" Speed="6000"
                 ProductionCounter="5425">
            <JobPhase JobID="Job-42" JobPartID="Front"
                Status="InProgress" QueueEntryID="I434" Amount="1343"
                StartTime="2016-12-28T10:40:00Z" PercentCompleted="31.66"
                Waste="85"/>
        </DeviceInfo>
    </SignalStatus>
</XJMF>
```

Since a Signal is an asynchronous message, the attribute `@refID` has to reference the initiating Query message. Signal messages are usually generated by the device. So if a proxy controller is involved in the communication, the attributes `@DeviceId` and `@Time` will differ between the XJMF’s Header element and that of the message.

The payload of the message is structured into one or multiple DeviceInfo subelements. Each DeviceInfo element represents the current status information of an individual device. Status information is, among other types of information, the speed of the device or other types of information. Additionally, the exact status name of the devices (here: “Production”) is part of the DeviceInfo element. More details pertaining to existing status values and the type of information that can be written to a DeviceInfo element can be read in the XJDF Specification.


## Subscriptions

Besides the synchronous method of querying information from a controller or a device, XJMF provides another mechanism to do this asynchronously. Instead of getting a synchronous Response Messages to a Query, a subscription initiates asynchronous Signal Messages from a controller or device periodically, and whenever a change of state occurs. For instance, an XJMF Status Signal Message can be emitted from a device every 30 seconds, and whenever its state changes. The periodical signal is similar to a heartbeat of the device (if a device could have a heartbeat), and each change of state immediately causes an additional signal. The tracking system therefore receives a periodical update on the counters, the amount of resource consumption, etc., but can also promptly track all (critical) changes of state related to the device. The following illustration shows the mechanics of a subscription:

<figure>
  <Image src={diagramXjmfStatusSubscription} alt="XJMF Status Subscription" />
  <figcaption>Figure: XJMF Status Subscription</figcaption>
</figure>

In order to set up a Subscription, the MIS has to send an XJMF Subscription Message to the controller (or device). The system on the receiving end creates a new persistent channel specific to the message, which then sends the requested Signal Messages to the target URL configured in the Subscription Message. The persistent channel can be removed by sending a StopPersistentChannel Command Message to the producer.

Subscriptions and their corresponding persistent channels are typically used by MIS’s in order to track the activity of connected controllers and devices. In general, Subscriptions can be used for any kind of production tracking purposes.

The most common three subscription types are Status, Notification, and Resource. A Status Signal Message contains “the general status of a device or a controller and the status of jobs associated with this device or controller. No job context is needed to issue a Status message” [@xjdf_ip1, chap. 7.18 "Status"]. The Notification Signal Message contains notifications produced by the controller or device. “Notification elements are also used to signal usual events due to any activities of a device, operator, etc. (e.g., scanning a barcode)” [@xjdf_ip1, chap. 7.10 "Notification"]. The Resource Signal Message contains information related to the Resources, such as consumption, and so on.

In order to turn a Query Message into a subscription, an additional Subscription element has to be written into the message’s body. The following is an example of an XJMF Status Subscription Message:

```xml title="Example: XJMF Status Subscription Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T13:22:01+02:00" />
    <QueryStatus>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T13:22:01+02:00" />
        <Subscription RepeatTime="30"
                URL="http://mis.example.org/xjmf" />
        <StatusQuParams />
    </QueryStatus>
</XJMF>
```

“Queries SHALL be subscribed by including a Subscription element that defines the details of the subscription. The receiver of the subscription SHALL initially send an empty Response Message to the sender. The receiver of the subscription SHALL send XJMF Signals whenever the conditions that were specified in the Subscription element are met. Such a subscribed query that requests multiple Signals is referred to as a ‘persistent channel’.

[...] If a Controller that does not support persistent channels is queried to set up a persistent channel, it SHALL answer the Query Message with a Response Message and set the `@ReturnCode` to ‘111’” [@xjdf_ip1, chap. 9.6.2 "Subscribing for Signals"].

The conditions in the above example stipulate sending a Signal Message at least every 30 seconds, as specified in the attribute `@RepeatTime`. The attribute `@URL` defines the target URL to which the Signal Message is to be sent.

### Persistent Channel

A persistent channel is responsible for sending asynchronous Signal Messages (periodically) to a subscriber. Each channel is defined by its ChannelID, the subscribing message type, the DeviceID, and the URL of the receiving system. Furthermore, each channel has additional attributes such as `@RepeatTime`, `@RetryPolicy`, and `@ChannelMode` in order to configure their behavior. The following table shows all relevant attributes relating to persistent channels:

| Attribute | Filter | Description |
| --- | --- | --- |
| `ChannelID` (required) | yes | The unique identifier of the persistent channel. “ChannelID specifies the ID of the Query message that initiated the Subscription. `@ChannelID` SHALL match `Header/@refID` of all Signals that comprise this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@ChannelID]. |
| `DeviceID` (required) | yes | “`@DeviceID` of the controller that subscribed for the persistent channel. `@DeviceID` SHALL match `@DeviceID` of the query that subscribed for this persistent channel” [@xjdf_ip1, chap. 7 Table 7.27: SubscriptionInfo/@DeviceID]. |
| `MessageType` (required) | yes | The message type of the Query Message being subscribed. For instance, in case a QueryStatus has created this channel, this Property has the value “Status”. |
| `URL` (required) | yes | “URL of the persistent channel receiving end” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@URL]. |
| `RepeatTime` | no | Update of the Signal Message “every `@RepeatTime` seconds. If defined, the Signal is generated periodically independent of any other trigger conditions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RepeatTime]. |
| `ChannelMode` | no | “Specifies reliability of persistent channel, and whether it is required or just preferred” [@xjdf_ip1, chap. 7.2.1.1 "Subscription/@ChannelMode"]. |
| `RetryPolicy` | no | “For reliable subscriptions. Indicates whether or not signals should be retried indefinitely, or only until the next Signal from the same Subscription (i.e., has the same `Header/@refID`) would be sent. `@RetryPolicy` is ignored for non-reliable subscriptions” [@xjdf_ip1, chap. 7 Table 7.5: Subscription/@RetryPolicy]. |

More details about the attributes and their effects on a production system can be read in the XJDF Specification. “Persistent channels SHOULD be maintained even when a device is powered off and powered on again” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].

While Query Messages containing a Subscription element set up a new persistent channel, the XJMF StopPersistentChannel Command Message removes a persistent channel. “No more Signal Messages are sent to the Controller once the command has been issued. A certain subset of signals MAY be addressed for unsubscription by specifying a StopPersChParams Element” [@xjdf_ip1, chap. 7.19 "StopPersistentChannel"]. The following is an example of such a Command Message:

```xml title="Example: XJMF StopPersistentChannel Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-15T15:26:59+02:00" />
    <CommandStopPersistentChannel>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-15T15:26:59+02:00" />
        <StopPersChParams URL="http://mis.example.org/xjmf" />
    </CommandStopPersistentChannel>
</XJMF>
```

The Command Message example above deletes all persistent channels created by the device “DEVICE_ID_MIS” and which are targeted towards the URL “*http://mis.example.org/jmf*”. All attributes marked as Filter = “yes” in the persistent channel Attribute Table can be used in the StopPersChParams element as a means of defining a subset of persistent channels to be removed. Attributes that are not specified default to match anything.


## Submission of XJDF Documents

In order to transfer XJDF Documents between the MIS, controllers, and devices, XJMF provides a set of Command Messages. Each XJDF Document represents a job for a specific Gray Box. “In XJMF, a controller or device is assumed to have one input queue that accepts submitted jobs” [@xjdf_ip1, chap. 4.7 "Queue Support"]. “A queue is a representation of a device that receives, manipulates and stores multiple queue entry items for execution” [@xjdf_ip1, chap. 1 Table 1.4: Glossary (Queue)]. From the perspective of XJMF, an XJDF Document is a queue entry of a device. The XJDF Specification defines the following Command Messages and their corresponding Response Messages for queue entry handling:

| MessageType | Description |
| --- | --- |
| `CommandSubmitQueueEntry`<br/>`ResponseSubmitQueueEntry` | “A job is submitted to a queue in order to be executed” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandReturnQueueEntry`<br/>`ResponseReturnQueueEntry` | “Returns a job that had been submitted with a SubmitQueueEntry to the queue that represents the controller that originally submitted the job” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandResubmitQueueEntry`<br/>`ResponseResubmitQueueEntry` | “Replaces a queue entry without affecting the entry’s parameters. The command is used, for example, for late changes to a submitted XJDF” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandModifyQueueEntry`<br/>`ResponseModifyQueueEntry` | “Modifies the properties of one or more QueueEntry elements” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |
| `CommandRequestQueueEntry`<br/>`ResponseRequestQueueEntry` | “A new Job is requested by the Device. This message is used to signal that a device has processing resources available” [@xjdf_ip1, chap. 7 Table 7.9: List of XJMF Messages]. |

“SubmitQueueEntry initially submits a QueueEntry to a device. Modifications to a QueueEntry can be applied by using the ResubmitQueueEntry or ModifyQueueEntry command” [@xjdf_ip1, chap. 7.20 "SubmitQueueEntry"].

“The ReturnQueueEntry Message returns a job that had been submitted with a SubmitQueueEntry to the controller that originally submitted the job. Note that this command is sent from the device to a controller and not from controller to device as is the case with most other queue handling commands” [@xjdf_ip1, chap. 7.16 "ReturnQueueEntry"].

“Queue entries are accessed using a `@QueueEntryID` attribute, which the queue’s controller or device generates when it receives the submitted job, and which is returned in the SubmitQueueEntry Response Message.

`@QueueEntryID` SHALL uniquely identify an entry within the scope of one queue. An implementation is free to choose the algorithm that generates `@QueueEntryID` values” [@xjdf_ip1, chap. 9.1.1 "Queue Entry ID Generation"].

  <Image src={diagramXjmfQueueEntry} alt="XJMF QueueEntry Submission and Return" />
  <figcaption>Figure: XJMF QueueEntry Submission and Return</figcaption>
</figure>

The drawing in the above figure shows the most simple queue entry handling in an XJDF workflow. The XJDF Document is submitted to a controller (or device) and is returned at the end of the execution process. The following snippet contains the corresponding XJMF SubmitQueueEntry Command Messages:

```xml title="Example: XJMF SubmitQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_MIS"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandSubmitQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_MIS"
                Time="2016-11-12T12:11:39+02:00" />
        <QueueSubmissionParams
                URL="http://mis.example.org/xjdf/job-1234.xjdf"
                ReturnJMF="http://mis.example.org/xjmf" Priority="42"/>
    </CommandSubmitQueueEntry>
</XJMF>
```

In the XJDF SubmitQueueEntry Command Message, all submission relevant details are defined in the subelement QueueSubmissionParams. The attribute `@URL` references the XJDF Document to be submitted. The attribute `@ReturnJMF` specifies the URL to which the receiving device or controller has to send the asynchronous feedback as soon as the processing of the job has been accomplished. Additionally, the QueueSubmissionParams element allows the specification of job metadata as the priority. `@Priority` is a “number from 0 to 100, where ‘0’ = lowest priority and ‘100’ = maximum priority” [@xjdf_ip1, chap. 7 Table 7.81: QueueSubmissionParams/@Priority]. The way in which the priority influences the production order of the single jobs is explained in the XJDF Specification.

When sending this message to a controller or device, the corresponding Response Message might look something like the following:

```xml title="Example: XJMF SubmitQueueEntry Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <ResponseSubmitQueueEntry ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-12T12:11:39+02:00"/>
        <QueueEntry QueueEntryID="1" Priority="42"
                Status="Waiting" />
    </ResponseSubmitQueueEntry>
</XJMF>
```

The corresponding XJDF SubmitQueueEntry Response Message references the Command Message in the `@refID` attribute. Furthermore, there is a QueueEntry subelement which contains details about the newly created queue entry. The `@QueueEntryID` attribute defines the identifier of the queue entry as defined above. The `@Priority` has been adapted on a 1:1 ratio, while the attribute `@Status` defines the current status of the queue entry.

After the successful execution of the job, the queue entry is sent back to the MIS. Following is a snippet containing the XJMF ReturnQueueEntry Command Message:

```xml title="Example: XJMF ReturnQueueEntry Command Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <CommandReturnQueueEntry>
        <Header ID="MESSAGE_ID" DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-12T12:11:39+02:00" />
        <ReturnQueueEntryParams QueueEntryID="1"
                URL="http://controller.example.org/xjdf/job-1234.xjdf" />
    </CommandReturnQueueEntry>
</XJMF>
```

The XJMF ReturnQueueEntry Command Message is initiated by the controller (or device) and contains a ReturnQueueEntryParams subelement. The subelement specifies the queue entries identifier (`@QueueEntryID`) in addition to the reference to where to locate the XJDF Document to send back. As feedback, the MIS returns the Response Message seen below in order to confirm the successful processing of the Command Message. The response does not specify any specific details:

```xml title="Example: XJMF ReturnQueueEntry Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-12T12:11:39+02:00" />
    <ResponseReturnQueueEntry ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="DEVICE_ID_CONTROLLER"
                Time="2016-11-12T12:11:39+02:00" />
    </ResponseReturnQueueEntry>
</XJMF>
```


## Interchange Protocol

“XJDF and XJMF SHOULD be exchanged over a network by using http […] or https. Controllers and devices SHOULD implement an http server. […] Controllers and devices SHOULD provide insecure http without a TLS layer for better interoperability” [@xjdf_ip1, chap. 9.5 "XJDF and XJMF Interchange Protocol"]. “XJMF Messaging does not specify a standard port” [@xjdf_ip1, chap. 9.5.1 "HTTP Port"].

“A sender SHALL use an http POST request to transmit an XJMF that contains XJMF Queries, XJMF Commands and XJMF Signals to an HTTP server. The contents SHALL be placed in the body of the http request. […].

The receiver SHALL package response messages as raw XML. The body of an HTTP response to an XJMF that contains only XJMF Signals that are not defined as reliable (`@ChanelMode`!="Reliable") MAY be empty” [@xjdf_ip1, chap. 9.5.2 "HTTP Request Method"].

To conclude, a table containing the most important interchange protocol parameters is presented here:

| Parameter | Value |
| --- | --- |
| Protocol | HTTP / HTTPS |
| Port | any |
| Request Method | POST |
| Payload Location | Body |

### Packaging

XJMF Messages may reference XJDF Documents, and XJDF Documents may reference external digital assets such as a customer’s artwork, or a Color Profile. A data transaction may therefore become complex. When, for instance, a job is being submitted from an MIS to a device, an XJMF SubmitQueueEntry Command message is initially sent. The command messages reference an XJDF Document provided on the MIS’s internal http server which has to be downloaded by the device. Next, the XJDF Document has to be interpreted by the device; if there are other external references, these also have to be downloaded from their source. In some circumstances, these “dependency chains” make a job submission fragile and complicated.

In order to reduce the amount of complexity during job submission, XJDF allows for the packaging of all files involved into a single ZIP archive. An XJMF ZIP Package contains a single XJMF Message, the XJDF Document to which it refers, and - if they exist - the digital assets to which the XJMF and XJDF refer to. “Zip is a de facto industry standard for packaging and compressing data. Directory structures can be encoded in a ZIP package” [@xjdf_ip1, chap. 9.7.2 "ZIP Packaging"]. Details can be found at: *https://www.pkware.com/support/zip-app-note/*.

When processing a ZIP package, a unique entry point needs to be defined. Therefore, the XJDF Specification defines the root XJMF. “The root XJMF SHALL be named root.xjmf and SHALL reside in the root directory of the ZIP package” [@xjdf_ip1, chap. 9.7.2.1 "Identifying the Root XJMF"]. Below is a screenshot of a root directory of a ZIP package:

<figure>
  <Image src={screenZipRoot} alt="Root Directory ('/') of the ZIP Archive" />
  <figcaption>Figure: Root Directory (“/”) of the ZIP Archive</figcaption>
</figure>

As shown in the figure, there is a file called “root.xjmf” in the ZIP package’s root directory. This is the first file to be interpreted by the recipient when unpacking and processing the archive. “Referenced digital assets that reside in the ZIP package, [...] SHALL be referenced as local URLs. The current URL for calculating local URLs SHALL be the root of the ZIP package, regardless of the location of the referring digital asset within the ZIP package. Digital assets other than the root.xjmf MAY be placed in a directory tree structure within the ZIP file” [@xjdf_ip1, chap. 9.7.2.2 "Referencing Digital Assets within a ZIP Package"]. The next screenshot below reveals the content of the subfolder “assets”:

<figure>
  <Image src={screenZipAssets} alt="Assets Subdirectory ('/assets/') of the ZIP Archive" />
  <figcaption>Figure: Assets Subdirectory (“/assets/”) of the ZIP Archive</figcaption>
</figure>

In XJMF and XJDF, most digital assets (including XJDF Documents) are referenced by an `@URL` attribute. The attribute can either references files in the file system, or it can define an http address for downloading the asset.

When packaging a ZIP archive, all assets (or a subset) can be packed into the zip archive. Afterwards, the appropriate `@URL` values in the XJMF Message and XJDF Document have to be updated to the new inner-zip-package location. The reference of the XJDF Document “doc.xjdf” in the root XJMF Message simply becomes “doc.xjdf” and the location of the “asset_2.jpg” has to be updated to “assets/asset_2.jpg”.

“XJMF messages that do not refer to XJDF or external digital assets SHOULD NOT be packaged as zip. Digital assets that are not included in the zip package MAY be referenced. Multiple XJMF messages SHALL NOT be packaged in one zip package” [@xjdf_ip1, chap. 9.7 "XJDF Packaging"].

“The following MIME types and extensions SHOULD be used when storing XJDF or XJMF as files or when a MIME type is required, e.g. when setting the http Content-Type header:” [@xjdf_ip1, chap. 9.7.1 "MIME Types and File Extensions"]

### Error Handling

“Error handling is an implementation-dependent feature of XJDF-based systems. The AuditPool element provides a container where errors that occur during the execution [...] SHOULD be logged using Notification elements. Notification elements MAY also be sent in XJMF messages” [@xjdf_ip1, chap. 9.3.8 "Error Handling"] as soon as an error occurs. Here is an XJDF example of an AuditPool element containing an Error Notification:

```xml title="Example: AuditPool Error Notification"
[...]
<AuditPool>
    [...]
    <AuditNotification>
        <Header DeviceID="DEVICE_ID" ID="MESSAGE_ID"
            Time="2016-11-14T16:57:24+02:00" />
        <Notification Class="Error" JobID="JOB_ID">
            <Event EventID="3092" EventValue="Paper stock is low." />
        </Notification>
    </AuditNotification>
    [...]
</AuditPool>
[...]
```

This example shows that the actual error information is part of the Notification element. “This Element contains information about individual events that occurred during processing” [@xjdf_ip1, chap. 7.10.3.1 "Notification"]. In this case, the event is an error. Using the attribute `@Class`, the Notification element can be classified. The value “Error” indicates that an error has occurred that requires user interaction. This value appears in situations such as when resources are missing, when major incompatibilities are detected, or when the toner is empty. The attribute `@JobID` brings the Notification into the right job context. Context information and classifications can of course be found in the XJDF Specification.

The entire Notification element is embedded in an AuditNotification element which is a direct subelement of AuditPool. However, instead (or in addition) of writing the Notification into the AuditPool of the XJDF Document, the Notification element can also be embedded into an XJMF Notification Signal message as a means of immediately sending the error information to the subscribing system.

```xml title="Example: XJMF Error Notification"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="DEVICE_ID_CONTROLLER"
            Time="2016-11-14T16:57:24+02:00" />
    <SignalNotification>
        <Header ID="I1234" refID="MESSAGE_ID"
            DeviceID="DEVICE_ID" Time="2016-11-14T16:57:24+02:00" />
        <Notification Class="Error" JobID="JOB_ID">
            <Event EventID="3092" EventValue="Paper stock is low." />
        </Notification>
    </SignalNotification>
</XJMF>
```


## XJMF Bootstrapping

XJMF Bootstrapping describes the process of service discovery when connecting a controller or device. “XJMF currently provides no mechanism for initial device discovery. Thus, the URL of an XJMF device needs to be provided to a controller outside of XJMF. Once the XJMF URL is known, a controller SHOULD follow the steps below:” [@xjdf_ip1, chap. 9.6.7 "XJMF Bootstrapping"]

<figure>
  <Image src={diagramXjmfBootstrapping} alt="XJMF Bootstrapping" />
  <figcaption>Figure: XJMF Bootstrapping</figcaption>
</figure>

This illustration shows an MIS, a controller, and two devices. The focus in this illustration lies on the communication between the MIS and the controller. Each box visualize a synchronous communication between both. In all three boxes, the MIS sends a Query Message to the controller and receives a synchronous Response message in return. The combination of the three boxes is also known as XJMF Bootstrapping. The XJMF Bootstrapping consists of the steps “Messages Discovery”, “Devices Discovery”, and “Subscriptions Discovery”.

Bootstrapping is not limited to the MIS-to-Controller communication but it is also valid for the Controller-to-Device or MIS-to-Device communication.

### Step 1: Message Discovery

In the first step, the initiating system sends an XJMF KnownMessages Query Message to the system for it to detect. “The KnownMessages Query Message returns a list of all Message types that are supported by the controller” [@xjdf_ip1, chap. 7.7 "KnownMessages"] or device. The initiating system therefore gets an idea of which XJMF functionality is supported by the called system. Below is an example of such an XJMF KnownMessages Query Message:

```xml title="Example: XJMF KnownMessages Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T19:22:28+02:00" />
    <QueryKnownMessages>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T19:22:28+02:00" />
    </QueryKnownMessages>
</XJMF>
```

In most situations, an empty XJMF KnownMessages Query Message is enough to obtain a sufficient reply. The synchronous response of the Query Message is an XJMF KnownMessages Response Message:

```xml title="Example: XJMF KnownMessages Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-14T19:22:29+02:00" />
    <ResponseKnownMessages ReturnCode="0">
        <Header ID="I1234" refID="MESSAGE_ID"
                DeviceID="CONTROLLER_ID"
                Time="2016-11-14T19:22:29+02:00" />
        <MessageService Type="QueryKnownMessages"
                URLSchemes="http" />
        <MessageService Type="QueryKnownDevices"
                URLSchemes="http" />
        <MessageService Type="QueryKnownSubscriptions"
                URLSchemes="http" />
        <MessageService Type="CommandSubmitQueueEntry"
                URLSchemes="http" />
        <MessageService Type="CommandShutDown"
                URLSchemes="http" />
        <MessageService Type="QueryStatus"
                URLSchemes="http" />
        [...]
    </ResponseKnownMessages>
</XJMF>
```

The XJMF KnownMessages Response message references the initiating Query message by its ID using the `@refID` attribute. Furthermore, the Response message contains “a list of MessageService elements. Each MessageService specifies one explicit message type that is supported by the device” [@xjdf_ip1, chap. 7.7.2.1 "MessageService"]. The message’s name can be found as the value of the attribute `@Type`. The meanings of the remaining attributes can be read in the XJDF Specification.

### Step 2: Devices Discovery

In the second step of the XJMF Bootstrapping process, the devices connected to the controller or the device itself are being discovered. An XJMF KnownDevices Query Message is therefore sent to the recipient. “The KnownDevices Query Message requests information about the Devices that are controlled by a controller [...]. The response is a list of device elements” [@xjdf_ip1, chap. 7.6 "KnownDevices"]. Here is an example of such a Query Message:

```xml title="Example: XJMF KnownDevices Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:26:07+02:00" />
    <QueryKnownDevices>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
                Time="2016-11-14T20:26:07+02:00" />
        <DeviceFilter DeviceDetails="Brief"/>
    </QueryKnownDevices>
</XJMF>
```

The example has previously been shown in the section “Query Message”. The message contains a subelement DeviceFilter. “The DeviceFilter Element refines the list of Devices that are requested to be returned” [@xjdf_ip1, chap. 7.6.1.1 "DeviceFilter"]. The usage of the value “Brief” in the attribute `@DeviceDetails` stipulates that the response should only provide the attribute DeviceID for each device listed in the DeviceList element. The corresponding Response Message is as follows:

```xml title="Example: XJMF KnownDevices Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T11:51:14+02:00" />
    <ResponseKnownDevices ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T11:51:14+02:00" />
        <Device DeviceID="DEVICE-I" />
        <Device DeviceID="DEVICE-II" />
    </ResponseKnownDevices>
</XJMF>
```

The XJMF KnownDevices Response Messages lists all devices which are controlled by the controller. For the initial discovery, this information should be sufficient. Should more information be required, the attribute `@DeviceDetails` in the Query Message can be set to “Full” in order to obtain the maximum amount of available device information from the controller.

### Step 3: Subscriptions Discovery

The last step of the XJMF Bootstrapping process is the subscriptions discovery. “The KnownSubscriptions XJMF enables controllers to query devices for a list of active persistent channels” [@xjdf_ip1, chap. 7.8 "KnownSubscriptions"]. The following snippet shows the XJMF KnownSubscriptions Query Message:

```xml title="Example: XJMF KnownSubscriptions Query Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    <QueryKnownSubscriptions>
        <Header ID="MESSAGE_ID" DeviceID="MIS_ID"
            Time="2016-11-14T20:57:27+02:00" />
    </QueryKnownSubscriptions>
</XJMF>
```

The message is straightforward, as it does not require any subelements. An optional subelement is the SubscriptionFilter element. “The SubscriptionFilter element is a filter to limit the list of SubscriptionInfo elements that are returned in the KnownSubscriptions Response” [@xjdf_ip1, chap. 7.8.1.1 "SubscriptionFilter"]. All attributes which are marked as filterable in the table “Attributes of a persistent channel” in the section “Persistent Channel” can be selected to filter the result.

The response to an XJMF KnownSubscriptions Query Message is an XJMF KnownSubscriptions Response Message, and it contains all details requested. Below is an example of such a Response Message:

```xml title="Example: XJMF KnownSubscriptions Response Message"
<XJMF xmlns="http://www.CIP4.org/JDFSchema_2_0">
    <Header ID="XJMF_ID" DeviceID="CONTROLLER_ID"
            Time="2016-11-11T21:07:14+02:00" />
    <ResponseKnownSubscriptions ReturnCode="0">
        <Header ID="I42" refID="MESSAGE_ID" DeviceID="CONTROLLER_ID"
                Time="2016-11-11T21:07:14+02:00" />
        <SubscriptionInfo ChannelID="CNL_1" DeviceID="MIS_ID"
                MessageType="Status">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
        <SubscriptionInfo ChannelID="CNL_2" DeviceID="MIS_ID"
                MessageType="Notification">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
        <SubscriptionInfo ChannelID="CNL_2" DeviceID="MIS_ID"
                MessageType="Resource">
            <Subscription URL="http://mis.example.org/jmf"
                    RepeatTime="30" RetryPolicy="DiscardAtNextSignal"
                    ChannelMode="Reliable" />
        </SubscriptionInfo>
    </ResponseKnownSubscriptions>
</XJMF>
```

The body of the XJMF KnownSubscriptions Response Message is a list of SubscriptionInfo elements. Each Subscription element describes an individual persistent channel.

“A Controller SHOULD NOT send a new subscription if a matching subscription is already in place in the device. If the device does not support QueryKnownSubscriptions, the controller MAY create a new subscription. A device that receives a subscription of the same type to the same URL SHOULD replace the existing subscription with the new subscription.

A controller SHOULD remove persistent channels that are no longer evaluated by sending a CommandStopPersistentChannel to a device” [@xjdf_ip1, chap. 9.6.3 "Managing Persistent Channels"].


## Piping (Overlapping Processing)

Up to now, XJMF Messages and XJDF Documents have only been presented for communication purposes within a production hierarchy. The MIS sends job information to lower level controllers and devices for execution, and, when finished, the information is sent back to the MIS system. In such an architecture, all processes are executed in serial (one after another), or sometimes even in parallel (especially in prepress data preparation). However, XJMF also provides communication methods for linking devices directly to each other.

“Some processes, e.g. a long print run, take a long time to complete while constantly creating intermediate output that is already available for processing by a subsequent process prior to completion of the initial process. In overlapping processing, the controller sends an XJDF to the initial device and does not wait until the first XJDF has been processed before sending a subsequent XJDF that describes the next process step of the same job to a different device.

The subsequent device MAY begin processing as soon as the initial device has produced sufficient resources for the subsequent device. The communication between the devices SHOULD use CommandPipeControl messages” [@xjdf_ip1, chap. 9.3.5 "Overlapping Processing"].

XJMF Piping can also be used in fully automated digital production lines, such as a Book-on-Demand production system. This type of system consists of a digital press of vendor A, and a finishing unit of vendor B. Both devices have to work closely together. For instance, when the press is interrupted, the finishing unit also has to pause, and vice versa. Another case would be that of the finishing unit wasting a book. In this situation, the press requires the information to reprint the book. All of these procedures and more can be standardized by way of using XJMF Pipes.

As piping is an advanced XJMF functionality, its details and intricacies are beyond the scope of this book but can be found in the XJDF Specification in the chapter “9.3.5 Overlapping Processing”.
