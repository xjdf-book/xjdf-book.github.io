“Interoperability Conformance Specifications (i.e., ICS documents) are developed by CIP4 working committees. They establish the minimum XJDF support requirements for devices of a common class, including expected behavior. An ICS document can subset XJDF but can not expand upon XJDF [...]. Once published, ICS documents will form the basis for testing and certification by CIP4-sanctioned facilities. XJDF-enabled products that pass these tests will be deemed ‘XJDF Certified’ to conform to an identified level of one or more ICS documents and will be permitted upon certification to use a ‘XJDF Certified’ logo in connection with certified XJDF-enabled products” [@xjdf_ip1, chap. 1.8.2 "Interoperability Conformance Specifications"].

Each ICS Document is maintained by a dedicated CIP4 Working Group and focuses on a specific integration domain. For example, the **“MIS to Conventional Printing – Sheetfed ICS”** (`MISCPS`) defines the interface between an MIS and a sheetfed offset press, whereas the **“MIS to Finishing ICS”** (`MISFin`) defines the interface between an MIS and postpress finishing equipment. The complete list of published ICS Documents is available on the CIP4 website (*https://www.cip4.org*).

Technically, an ICS Document defines one or more standardized **Gray Boxes**, specifying the required process types (`@Types`) along with their mandatory and optional input and output resources:

Whereas the master XJDF Specification defines the entire universe of valid XJDF elements and attributes, an ICS Document specifies the exact subset of elements, attributes, and XJMF messages that a conforming sender (Controller/MIS) must write and a conforming receiver (Device) must read for a given Gray Box—acting as a concrete technical interface contract between the two parties.

“An ICS specifies a set of Conformance Requirements that a conforming XJDF-enabled Product SHALL meet in order to achieve interoperability with other conforming XJDF-enabled Products that meet the same Conformance Requirements” [@cip4_base_ics, Glossary "Conformance Requirement"]. Each ICS Document defines up to three incremental conformance levels (Levels 1, 2, and optionally 3, plus Level 0 where applicable): “Due to the incremental nature of the ICS levels except for Level 0, a controller or device that conforms to a higher level is able to interoperate with a controller or device, respectively that conforms to a lower level by using this lower level for all communication” [@cip4_base_ics, chap. 4.2 "Interoperability of Levels"].

An XJDF Document that conforms to an ICS Gray Box declares its conformance using two attributes on the root `XJDF` element—`@ICSVersions` and `@Category`. Below is the root `XJDF` element of our earlier saddle-stitching example configured to conform to the `"MISFin.StitchFin"` Gray Box of the *MIS to Finishing ICS*:

```xml title="Example: XJDF Stub of Gray Box 'MISFin.StitchFin'"
<XJDF JobID="JOB-1234" Types="Collecting Stitching Trimming"
        Category="MISFin.StitchFin" ICSVersions="MISFin_L1-2.0"
        xmlns="http://www.CIP4.org/JDFSchema_2_0">
    [...]
</XJDF>
```

* **`@ICSVersions`:** “`@ICSVersions` SHALL list all CIP4 Interoperability Conformance Specification (ICS) Versions that this XJDF complies with. Value format is: `<ICSName>_L<ICSLevel>-<ICSVersion>`” [@xjdf_ip1, chap. 3 Table 3.1: XJDF/@ICSVersions]. In the example above, `"MISFin_L1-2.0"` declares conformance to Level 1 of the *MIS to Finishing ICS* (`MISFin`), version 2.0.
* **`@Category`:** “specifies the named category of this XJDF” [@xjdf_ip1, chap. 3 Table 3.1: XJDF/@Category]. For ICS-conformant documents, `@Category` is formatted as `<ICSAbbreviation>.<GrayBoxName>`—here `"MISFin.StitchFin"`, where `"StitchFin"` is the ICS Gray Box that “produces a stitched Product” [@cip4_misfin_ics, chap. 6.7 "GB StitchFin"].

In short, while the XJDF Specification provides the common industry vocabulary and foundational data model across the entire graphic arts domain, **real-world plug-and-play interoperability is driven by the ICS Documents**. When building a standardized XJDF integration, developers should always start from the relevant ICS Document rather than the full XJDF Specification. If no official CIP4 ICS Document exists yet for a particular integration scenario (such as a specialized cloud service or custom Web-To-Print interface), it is best practice to draft a concise internal ICS profile defining the agreed-upon Gray Boxes, resources, and attributes—and, where appropriate, contribute it to CIP4 as the basis for a new industry-wide ICS standard.
